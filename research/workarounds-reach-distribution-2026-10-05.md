## (a) In-product update

**Today [R]:** `doctor` prints "shotfleet X is out" from `GET /download/VERSION`, with no `context=` (works on 0.1.1 and later, which read `/private/etc/ssl/cert.pem`). `install.sh` is the updater: `rm -rf "$APP"` then `mv`; the licence sits outside the folder, so it survives. README (0.1.2) says "Update: run the install line again". C091 records an owner decision that `--version` stays offline and only `doctor` asks the site; the privacy page says exactly that, and `G1NothingLeavesTheMac` (claims line 66) lists the allowed `urlopen` sites.

**Safe design if built (cheapest form):** `shotfleet update` asks, then runs `/bin/sh` on the installer, nothing more. The program writes no download code: curl does TLS, and the Python process only waits and then prints. Improve `install.sh` (benefits the `curl | sh` path too): (1) unpack and verify first: `codesign --verify --strict -R='anchor apple generic and certificate leaf[subject.OU] = "2357A78TMR" and notarized'` on the new program. **Measured here:** exit 0 on the 0.1.1 release file, exit 3 with another team id, `/bin/ls` fails `notarized`; it works on a bare executable, where `spctl --assess` says "rejected (does not seem to be an app)" [M]. Drop `notarized` offline (the ticket lookup is online [I]) and keep the team-id requirement, which is offline [M for team id; the offline behaviour of `notarized` untested]. This closes the real gap: the checksum comes from the same host as the file, and a Python- or curl-fetched file has no quarantine flag, so Gatekeeper never looks at it. (2) Swap safely: `mv app app.old && mv new app`, run `app/shotfleet --version`, restore `app.old` if it fails, delete it if it works (APFS `renamex_np` swap is an option, not needed). (3) Refuse when the running program is not the `install.sh` copy (`.pkg` installs live in root-owned `/usr/local/lib/shotfleet`, Homebrew in the Cellar): print `brew upgrade shotfleet` or the installer line. (4) Offline: curl fails, nothing changes, exit 2 with the reason. (5) Keep the licence: untouched, it is a sibling file.

**Privacy and claims:** an explicit `update` is user-initiated, but the privacy page must gain one sentence ("`shotfleet update` downloads the release from this site; the request carries curl's user agent and your IP address, nothing else") and C091 plus DISTRIBUTION.md change with it. A notice in `run`/`export` that looks up the version is different: it is an automatic call from a command whose pitch is "nothing leaves your Mac", it breaks the sentence "doctor also asks this site", and a CI job would call out on every run. If ever built: daily cache, 2 s timeout, silent on failure, off with `SHOTFLEET_NO_UPDATE_CHECK=1`, `CI`, `--json` and a non-TTY, never in `check`. **Better, no network:** the build knows its own date; `run`/`export` print one line when the build is over about 60 days old ("this build is from 2026-10-05; `shotfleet doctor` says whether a newer one is out"). Nothing leaves the Mac, nothing to disclose, 1.5 h with a unit test and a fake clock.

**Where 0.1.0 buyers are stuck:** the 0.1.0 folder was built from Homebrew's Python for macOS 27.0 (52 of 56 Mach-O files at 27.0 [M, platform note]); per the coordinator it probably cannot start below macOS 26.3. Those buyers cannot run any in-product path, and on macOS 26.3 and later the 0.1.0 `doctor` notice probably fails TLS without Homebrew (INFERENCE, release-engineering note, untested). The only channel is email: every buyer has a Gumroad receipt. Text: "shotfleet 0.1.1 and later run on macOS 13 or newer; update with `curl -fsSL https://shotfleet.com/install.sh | sh`; your key stays." Count to check first: the strategy note says 0 real sales, so the 0.1.0 audience may be the owner's own test purchases; look at Gumroad Sales before writing anything (owner).

**How to test without a build:** unit tests with a local HTTP server and a fake `codesign` on the PATH (existing pattern in `tests/test_release_scripts.py`); one end-to-end run on this Mac with the 0.1.1 and 0.1.2 tarballs from `shotfleet-rc-build`, in a temp HOME, against a local server (no device, light). **Hardware needed:** none. **Touches:** `site/public/install.sh`, `privacy.html`, C091, C113, DISTRIBUTION.md, README "Update" line, `tools/golive/smoke.sh` (splits `install.sh` at the `tar -xzf` line, a change near it breaks the smoke test).

## (b) Homebrew tap

**Feasible, done in draft and tested [M].** Files in `research/proposed-tap/`: `Formula/shotfleet.rb` (template), `render-formula.sh <version> <tarball> <url>` (SHA-256 from the tested tarball), `README.md`. A throwaway tap (`brew tap-new --no-git`, removed afterwards with `brew untap`, formula uninstalled) gave:
- `brew audit --strict --formula`: exit 0, no findings. `brew install` of the 0.1.1 release tarball through a `file://` URL: 2 s, 20 files. `brew test` ran `shotfleet --version`: passed.
- After install: `codesign --verify --deep --strict` exit 0 and the team-id plus `notarized` requirement exit 0. Homebrew 7 does not strip or re-sign the files; the install has no `com.apple.quarantine` attribute. The quarantine code in Homebrew lives only under `Library/Homebrew/cask/` (grep [M]): **formulae downloads are never quarantined, casks are.** A cask would also work (Gatekeeper checks a notarized CLI online on first run, as `build.sh` already tests) but only needs more: since 2026-09-01 the official cask tap drops casks that fail Gatekeeper, and `--no-quarantine` is gone (Homebrew issue 20755 [R]); that does not bind a personal tap, and shotfleet passes anyway. **Use a formula**: `brew upgrade` works, no `--cask`.
- Homebrew 7 **tap trust** [R, docs.brew.sh/Tap-Trust]: `brew install noloman/shotfleet/shotfleet` (fully qualified) works and trusts that one formula; `brew tap noloman/shotfleet` then `brew install shotfleet` fails until `brew trust`. So publish only the fully qualified line.
- Needs no bottle (the formula installs a prebuilt folder, `depends_on arch: :arm64` and `macos: :ventura`).

**What the tap repo holds:** `Formula/shotfleet.rb`, a 10-line README. The owner already runs `noloman/homebrew-keysi` with a script-generated cask and a "do not edit by hand" README, so the pattern exists. **Blocker:** the site serves only the unversioned `/download/shotfleet-macos-arm64.tar.gz` [R, `publish.sh`]; a formula's SHA-256 would break at the next release, and `brew install` of an older formula would fail. Fix = item 2 (versioned path, or release assets in `noloman/shotfleet-releases`). Also: `livecheck` points at `/download/VERSION` (works, untested against the live site). Docs touched: DISTRIBUTION.md Homebrew rows, README "Install" (one line), C092 text. Test on release: render, `brew audit --strict`, `brew install` from the real URL on one clean Mac. Hardware: none beyond this Mac. Public repo required (owner decision: DISTRIBUTION.md "kept for later").

## (c) GitHub Action

**Draft files, offline-tested [M]:** `research/proposed-action/` (`action.yml`, `summarize.py`, `example-workflow.yml`, `README.md`, `selfcheck.sh`, `steptest.sh`). The YAML parses (Ruby); the "Run shotfleet" step was run with a fake `shotfleet`: problems fail the step, `fail-on-problems: false` passes, a `free tier:` line fails a `run` with exit 2 unless `require-licence: false`, an unknown command is refused. Not run on GitHub, so `actions/cache@v4` and `$GITHUB_PATH` are unexercised.

Design: refuse non-macOS and non-arm64 (`hw.optional.arm64`); `install.sh`; then the **team-id plus notarized requirement** on the installed program (the check `install.sh` lacks, section a); run `check` (default), `doctor` or `run` with `--json`; write problems to the job summary; outputs `exit-code` and `problems`. `SHOTFLEET_KEY` goes in only as the `key` input from a secret, only to the run step, only when non-empty. **Licence behaviour:** missing or refused key makes `run` capture 2 languages and exit 0, and a Gumroad outage counts as licensed (both documented); the action cannot tell an outage from a good key, so `require-licence` guards only the first case. `cache-home` caches `~/.shotfleet` (Maestro, Java) for `run`; `check` needs no cache (10 MB program).

**Cost [R, GitHub docs via search; measured job times from the platform note]:** macOS arm64 standard runner $0.062 a minute in private repos, each macOS minute uses 10 of the included minutes (2,000 free is about 200 macOS minutes), free in public repos; measured install plus `doctor` plus `check` was 16 s on macos-14 and 29 s on macos-15, so about 1 billed minute (about $0.06) if no app build is needed (`--strings` avoids `xcodebuild`, which dominates). A hosted macOS runner has 3 vCPU and no nested virtualization, so no Android emulator: the action is a **check** action; `run` only as far as the runner hosts simulators (4 simulators on 3 vCPUs untested).

Not done: version pinning (blocked by item 2); one real run (owner's cost rule; about $0.06); the Marketplace listing (a public repo with `action.yml` at its root and the owner accepting the Marketplace terms). README "In CI" says the recipe has not run on GitHub: keep saying so until it has. The same action is the answer for **Intel-Mac developers**: their CI can run `check`.

## (d) fastlane plugin

**Feasible, not worth it.** A plugin is a Ruby gem `fastlane-plugin-shotfleet` (scaffold `fastlane new_plugin`) with actions that shell out to the CLI; needs a RubyGems account (owner) and Ruby tests. The slot is proven: `fastlane-plugin-maestro` (v0.0.9, 111k downloads, 22 stars, last release 2024-12 [R, RubyGems]), but that says plugins get installed, not that buyers want this one. The handoff is already documented and runs without a plugin: README step 6 and the hook `after_export = 'fastlane deliver --skip_binary_upload --skip_metadata --overwrite_screenshots --screenshots_path "$SHOTFLEET_FASTLANE/screenshots"'`, plus `shotfleet check fastlane/` right before uploading. What the plugin would add is a name in `fastlane search_plugins` and a Ruby-typed result. Documented lane, to add to the README (not tested here, `sh` runs from the `fastlane/` folder):

```ruby
lane :check_screenshots do
  sh("shotfleet check screenshots --strings '../Resources/*/Localizable.strings' --json > ../check.json")  # exit 1 fails the lane
end
lane :screenshots_upload do
  sh("shotfleet check screenshots --app ../build/MyApp.app")
  deliver(skip_binary_upload: true, skip_metadata: true, overwrite_screenshots: true, force: true)
end
```
Effort 0.5 h for the lane, 6 to 8 h for a plugin with tests. Recommendation: lane yes, plugin no; reconsider only if someone asks for `snapshot` to call shotfleet directly.

## (e) Intel Macs

**What it takes [R/M]:** the toolchain is ready: Maestro's iOS driver is x86_64+arm64 in 2.0.10 and 2.11.0 [M, platform note], Google ships `emulator-darwin_x64` and `commandlinetools-mac_x86_64` (manifest, 2026-10-05), `host_abi` already picks x86_64, and `swiftc -target x86_64-apple-macos13.0` compiled the OCR helper and `lipo` made a fat one [M, platform note]. What is missing is the program: PyInstaller can make `--target-arch universal2` only when **every** binary in the environment is fat (python.org's installer is universal2; Homebrew's and, to my knowledge, python-build-standalone's are single-arch [I from PyInstaller docs and issues 7740, 8429; standalone not confirmed]); the realistic way is a second, separate x86_64 build and tarball, not a fat one.
Cost list: an x86_64 Python (Rosetta is not installed on this Mac, "Bad CPU type" [M, platform note]; installing it is a download) or GitHub's `macos-15-intel`, which exists only until **August 2027** [R, runner-images], and has no signing identities, so signing still needs the owner's keychain; a second notarization of program and package; `install.sh` picks by arch (with the Rosetta fix, item 10); `publish.sh`, `verify-release.sh`, `preflight.sh`, `smoke.sh` and `tests/test_release_scripts.py` all assume one tarball; per-arch manifest and checksum; docs and claim rows (C002, C113, terms, site, llms.txt, README Limits, `skill/shotfleet-ci`). Effort **L, 12 to 16 h**, plus an Intel Mac with Xcode 26 for the only test that matters (an iOS run: Xcode 26 and iOS 26 simulators have never been used with shotfleet; every iOS run so far was Xcode 27 [R]). Risk high.
**Demand:** none recorded (no ask in STATUS, marketing, or the strategy note; a first-hand count of asks is 0). The market is shrinking by Apple's schedule: macOS 26 is the last release for Intel Macs, macOS 27 (2026-09-14) is Apple-silicon only, and only four Intel models run Tahoe (2019 16" MacBook Pro, 2020 4-port 13" MacBook Pro, 2020 27" iMac, 2019 Mac Pro) [R, MacRumors and others via search]. From April 2027 App Store uploads need the iOS 27 SDK, i.e. Xcode 27 [R, Apple developer news via search]; whether Xcode 27 runs on macOS 26 is **not verified** (I assume not, [I]: this Mac runs Xcode 27 on macOS 27), so an Intel developer could not ship an iOS update after that date. **Recommendation: no.** Say "Apple silicon only; `check` runs in CI on an Apple-silicon runner" (item 3). Revisit at three independent asks, and then for Android-only buyers.

## (f) Linux

**Reality [R, docs/linux.md]:** x86_64 with `/dev/kvm` only. E1 (2026-10-03): the Android fixture passed 13/13 in 8 min 13 s with **one** emulator on a 2-core, 7 GB GitHub runner after seven attempts and several real fixes (SDK path with `..`, `XDG_CONFIG_HOME`, the 12 GB userdata partition, dialogs over screenshots, the `package` service race). Two emulators on 2 cores failed in four runs ("Process system isn't responding"); two on 4+ cores, a real 18-language app on Linux and any shipped Linux build are untried. `check` works anywhere with Tesseract. iOS is impossible. **ARM Linux:** Google's emulator source supports ARM64 hosts since 30.0.26 (2020), but only with `-gpu swiftshader_indirect` and snapshots maybe not working, and no prebuilt Linux arm64 emulator package was in Google's manifest [R emulator release notes; M manifest, platform note]; shotfleet snapshot-boots its emulators, so assume it does not work. `docs/linux.md` still says "x86_64 or ARM Linux with `/dev/kvm`" and `host_abi()` returns `arm64-v8a` on aarch64: that sentence is wrong and should be x86_64 only.

**Packaging options:** (1) nothing: source install, as now; (2) `packaging/build-linux.sh` tarball (20 MB, 13 s, unsigned, ran `check` and `doctor` [R]) plus a 15-line `install-linux.sh` with SHA-256, apt hints for Tesseract and `aapt`; build on an old glibc (a 22.04 container) so it runs widely [I]. The licence gate applies "in released builds only" (frozen), so a frozen Linux build enforces Gumroad keys: untested on Linux. Effort S, 3 h; hardware for the real test: a 4+ core Linux box with KVM. A GitHub 4-core test is awkward: larger runners need a Team or Enterprise organization and are not available to personal accounts [R], the repo is `noloman` (personal); public repos' standard Linux runner may be 4 vCPU [I, not verified]. **Recommendation:** no Linux release. Claim publicly only what README says now: "`check` and the Android readers run from source on Linux with Tesseract; `run` on a Linux emulator passed one fixture with one emulator and is not supported." Do not write "Linux support", "ARM Linux" or "CI on Linux". Add the E1 summary to the Linux page of the site only if the owner wants it. Windows: no.
