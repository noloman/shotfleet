Date: 2026-10-02. Research and design only: no simulator, emulator or Maestro run, no installs, no repo files edited.
Code read: `README.md`, `shotfleet.py` at commit 19a0884 (`cmd_doctor`, `java_ok`, `cmd_init`, `device_build`, `WRONG_BUILD`, `build_hint`, `android_pool`, `ocr_tool`, `read_text`, `translate_flow`, `load_config`, `cmd_export`), `tools/release.sh`, `tools/build.sh`, `DISTRIBUTION.md`, `PLAN.md`, `research/first-run.md`.

Labels used below: **[verified]** = I saw it on this Mac or in a primary source today (source named). **[derived]** = follows from Homebrew's source on this Mac but I did not run the failing case. **[unverified]** = needs a clean Mac or a download I was not allowed to make.

## 0. Findings that change the plan

1. **Homebrew 7 refuses formulae from untrusted third-party taps, and a dependency in another tap is not trusted automatically.** [verified: this Mac runs Homebrew 7.0.7; `brew trust --help`; `Library/Homebrew/trust.rb`, `cmd/install.rb`; brew.sh/2026/09/13/homebrew-7.0.0]. `brew install <tap>/<formula>` with the fully qualified name trusts that one formula (`Trust.trust_fully_qualified_items!(args.named)`). `require_trusted_formula!` lets a formula through only if the tap is trusted, the formula is in trust.json, or its full name is in `ARGV`. Evidence on this Mac: `~/.homebrew/trust.json` lists `noloman/keysi/keysi` and `mobai-app/tap/simslim` as item-level trusts, while `brew tap-info noloman/keysi` says "Untrusted" for the tap. So:
   - `brew install noloman/tap/shotfleet` works. `brew tap noloman/tap && brew install shotfleet` (bare name) fails until `brew trust noloman/tap`. **Every doc and the site must show the fully qualified one-liner.**
   - A formula that says `depends_on "mobile-dev-inc/tap/maestro"` [derived] would be refused with "Refusing to load formula mobile-dev-inc/tap/maestro from untrusted tap", because that name is not on the command line. Maestro's own install page now tells users to run `brew trust --formula mobile-dev-inc/tap/maestro` before installing (docs.maestro.dev/maestro-cli/how-to-install-maestro-cli.md). We should not inherit that step.
2. **An official Maestro tap exists, but not in homebrew-core.** [verified] `mobile-dev-inc/homebrew-tap` has `Formula/maestro.rb` (generated by JReleaser, 2026-09-29): `cli-2.11.0/maestro.zip`, sha256 `5384593c...`, `depends_on "openjdk" => "17+"`, `bin.install_symlink "#{libexec}/bin/maestro"`. `brew info mobile-dev-inc/tap/maestro` here fails only because the tap is not added. **`brew info maestro` resolves to an unrelated cask** (Maestro.app, runmaestro.ai, v0.17.5, homebrew-cask). Never tell anyone to `brew install maestro`.
3. **The doctor fix for Java does not work today.** [verified] `cmd_doctor` says `brew install openjdk@17`. That formula is `keg_only :versioned_formula` and its own caveat says the system Java wrappers only find it after `sudo ln -sfn ... /Library/Java/JavaVirtualMachines/openjdk-17.jdk`. `java_ok()` looks at `java` on PATH, so after the suggested install doctor still says MISSING. Maestro too: with a clean environment and no `JAVA_HOME`, the Maestro 2.0.10 on this Mac prints "ERROR: Java 17 or higher is required" (the stub finds Temurin 11 under /Library/Java), and with `JAVA_HOME=/opt/homebrew/opt/openjdk@17/libexec/openjdk.jdk/Contents/Home` it runs. **shotfleet must find a JDK itself and pass `JAVA_HOME` to every child process.** That also fixes Maestro's own Homebrew install, which has the same keg-only trap [derived].
4. Maestro's curl installer needs `java` on PATH (it exits "java not found"), refuses to run if a Homebrew Maestro is on PATH, and edits shell rc files [verified: `curl https://get.maestro.mobile.dev`]. The latest Maestro is **2.11.0** (published 2026-09-29, `maestro.zip` is **315 MB**, sha256 listed in the release); this Mac has 2.0.10 [verified]. The README says "Maestro 2.x"; which 2.x shotfleet is actually tested against is not written anywhere.
5. **The first OCR compile is silent.** [verified in code] `cmd_check` prints "macOS prepared its text recognition ..." only after the wait, and only if it took more than 20 s. PLAN.md measured 127 s on a loaded Mac and about 30 s on a quiet one. In `run`, `check` is the last step, so the silence arrives after a 10-minute capture.
6. **`xcodebuild -list` and `-showBuildSettings` have a side effect.** [verified] On copies of two real projects they resolved Swift packages and wrote **2.4 GB each** into `~/Library/Developer/Xcode/DerivedData/<name>-<hash>/SourcePackages`; the cold `-list` took 2 min 19 s on a busy Mac (the same project's `-showBuildSettings` then took 9 s). I deleted the two folders I created. `init` must not call them by default.
7. **DerivedData is volatile.** [verified, observed while researching] The four `Crossfit_Tracker-*` and two `Kuokka-*` folders I listed at the start (all worktree copies) were gone half an hour later, deleted by another session. Auto-discovery from DerivedData is a convenience, never the only path: `init --build` with our own `-derivedDataPath` is the reliable one.
8. **doctor already got two fixes since the audit** (Java check, swiftc skipped for the frozen binary), so those are not repeated here. Still wrong: the Maestro and Android fix strings, SDK discovery limited to `ANDROID_HOME` or `~/Library/Android/sdk`, `adb` required on PATH.

## 1. Maestro and Java

### What to ship

**Recommendation: our formula installs Java (`openjdk@21`, homebrew-core, implicitly trusted) and carries Maestro as a pinned `resource`.** Not `depends_on` the Maestro tap.

| Option | Buyer steps | Problems |
|---|---|---|
| A. `depends_on "mobile-dev-inc/tap/maestro"` | `brew trust --formula mobile-dev-inc/tap/maestro` first, then install | Untrusted-tap refusal [derived]; keg-only Java trap; two Maestros if the buyer already used the curl script; we cannot pin a tested version |
| B. Curl script in doctor's fix text (today) | one more manual step plus Java first | Needs `java` on PATH, edits `~/.zshrc`, conflicts with brew copy |
| **C. Formula: `depends_on "openjdk@21"` + `resource "maestro"` (pinned zip)** | none | 315 MB resource per version (Homebrew caches downloads, so upgrades that keep the same Maestro reuse it); we bump the pin only after our tests pass on it |
| D. shotfleet downloads Maestro and a JRE itself on first use | none | About 25 lines of downloader code; only needed for the non-Homebrew tarball. Temurin 21 JRE aarch64 macOS is 48 MB with a published checksum [verified: api.adoptium.net]. Skip until someone asks for a tarball install |

Formula sketch (replaces the heredoc in `tools/release.sh`):

```ruby
  depends_on arch: :arm64
  depends_on :macos
  depends_on "openjdk@21"          # Maestro needs 17+; 21 is the LTS we test with

  resource "maestro" do            # tested version; bump deliberately
    url "https://github.com/mobile-dev-inc/maestro/releases/download/cli-2.11.0/maestro.zip"
    sha256 "5384593cb4e7a106489e75a821d157dd43f4e438df6bc308b72e82c685e1283a"
  end

  def install
    bin.install "shotfleet"
    resource("maestro").stage { (libexec/"maestro").install Dir["*"] }   # zip has bin/ and lib/ (single top folder is stripped)
  end

  def caveats
    "Next: cd into your app's repo, then run: shotfleet init"
  end
```

[unverified] that the zip's single top-level folder is stripped the way the Maestro formula's `libexec.install Dir["*"]` implies, and that `sys.executable` of the PyInstaller binary resolves to the Cellar path. Test both in a clean Homebrew prefix before the first release. Do not add `HOMEBREW_NO_REQUIRE_TAP_TRUST` advice anywhere: it is deprecated and "will be removed in a later release" (`env_config.rb`).

### Code in shotfleet (about 30 lines, replaces `shutil.which("maestro")` in three places)

```python
def maestro_cmd():
    """SHOTFLEET_MAESTRO, else the Maestro our Homebrew formula installed next to us, else PATH."""
    bundled = Path(sys.executable).resolve().parent.parent / "libexec/maestro/bin/maestro"
    for c in (os.environ.get("SHOTFLEET_MAESTRO"), bundled, shutil.which("maestro")):
        if c and os.access(c, os.X_OK): return str(c)

def find_java(min_major=17):
    """A JDK home of at least min_major, or None. Order: JAVA_HOME, /usr/libexec/java_home, Homebrew kegs, sdkman, Android Studio."""
    cands = [os.environ.get("JAVA_HOME"), sh(["/usr/libexec/java_home", "-v", f"{min_major}+"]).stdout.strip(),
             *sorted(glob.glob("/opt/homebrew/opt/openjdk*/libexec/openjdk.jdk/Contents/Home"), reverse=True),
             str(Path.home() / ".sdkman/candidates/java/current"),
             "/Applications/Android Studio.app/Contents/jbr/Contents/Home"]
    for home in filter(None, cands):
        r = sh([f"{home}/bin/java", "-version"]) if Path(home, "bin/java").exists() else None
        m = r and re.search(r'version "(\d+)', r.stderr + r.stdout)
        if m and int(m[1]) >= min_major: return home

def tool_env():
    """Environment for every child (maestro, gradlew, sdkmanager, avdmanager): the JDK we found, adb reachable, Maestro quiet."""
    env = {**os.environ, "MAESTRO_CLI_NO_ANALYTICS": "1", "MAESTRO_DISABLE_UPDATE_CHECK": "1",
           "MAESTRO_CLI_ANALYSIS_NOTIFICATION_DISABLED": "1"}   # the last two are documented Maestro env vars
    if j := find_java(): env["JAVA_HOME"] = j
    if sdk := find_sdk(): env["ANDROID_HOME"] = str(sdk); env["PATH"] = f"{sdk}/platform-tools:{env['PATH']}"
    return env
```

(`MAESTRO_DISABLE_UPDATE_CHECK`, `MAESTRO_CLI_NO_ANALYTICS`, `MAESTRO_CLI_ANALYSIS_NOTIFICATION_DISABLED`: docs.maestro.dev/maestro-cli/environment-variables.md [verified]. Today only the analytics one is set, and only on two of the call sites.) Use `tool_env()` at both `run_guarded(["maestro", ...])` sites and for `avdmanager`. `Emu.adb` and Maestro both call `adb`; prepending `<sdk>/platform-tools` removes the "adb not found" case for buyers whose SDK came from the command-line tools.

## 2. Finding or building the app: `shotfleet init` with no arguments

### Verified facts about this Mac

- `~/Library/Developer/Xcode/DerivedData/<Name_with_underscores>-<28-char hash>/` holds `info.plist` with two keys, `WorkspacePath` (the `.xcodeproj` or `.xcworkspace`, may contain spaces: `.../iosApp/Crossfit Tracker.xcodeproj`) and `LastAccessedDate`. The hash does not identify the scheme.
- Products: `Build/Products/<Configuration>-iphonesimulator/<App>.app`; Watch apps sit in `Debug-watchsimulator/WatchApp.app`. A folder that was never built has no `info.plist` (`remoti-*` here had only `Logs/` and `SourcePackages/`).
- Several folders can point at copies of one project (this Mac had four for CrossfitTracker, all under `.claude/worktrees/`).
- Custom DerivedData location: `defaults read com.apple.dt.Xcode IDECustomDerivedDataLocation` is unset here; `IDEBuildLocationStyle` is `Unique`.
- Android: `./gradlew assembleDebug` output is `<module>/build/outputs/apk/[<flavor>/]debug/<module>-debug.apk` (CrossfitTracker: `androidApp/.../androidApp-debug.apk` **and** `wearApp/.../wearApp-debug.apk`; HackerNewsKMP: module `composeApp`). Settings use version-catalog aliases (`alias(libs.plugins.androidApplication)`), so grepping for `com.android.application` is unreliable.

### Matching rule (iOS)

```python
def derived_apps(cwd):
    root = Path.home() / "Library/Developer/Xcode/DerivedData"
    cwd, found = cwd.resolve(), []
    for plist in root.glob("*/info.plist"):
        ws = plistlib.loads(plist.read_bytes()).get("WorkspacePath")
        if not ws: continue
        proj = Path(ws).parent
        if proj == cwd or cwd in proj.parents: rel = proj.relative_to(cwd)    # build of a project below here
        elif proj in cwd.parents: rel = Path()                                # cwd is inside the project (iosApp/Sub)
        else: continue
        if any(p.startswith(".") for p in rel.parts): continue                # .claude/worktrees/..., .build: other copies
        found += plist.parent.glob("Build/Products/*-iphonesimulator/*.app")
    return sorted(found, key=lambda a: a.stat().st_mtime, reverse=True)
```

Then filter each `.app`: `DTPlatformName == iphonesimulator` (`device_build()` already reads it), bundle id not ending `.xctrunner`, has `CFBundleExecutable`. Prefer `Debug-*`, newest `mtime`. Print the choice and why: `iOS: Kuokka.app (Debug-iphonesimulator, built 2 h ago, from iosApp/Kuokka.xcodeproj)`, plus the other candidates in one line each so a wrong pick is visible. Warn when the `.app` is older than the newest source file? No: print the age only.

Android: `glob("**/build/outputs/apk/**/debug/*.apk")` to depth 5 from cwd, skipping `androidTest`, hidden folders and `build/` copies of other worktrees. Then `aapt2 dump badging` (already used by `init`): drop APKs whose badging has `uses-feature: name='android.hardware.type.watch'` or no `launchable-activity` (the Wear app next to the phone app) and take the newest. Two real phone APKs: list both, tell the user to run `init` per APK (init already rejects two of one kind).

When nothing is found, print the build commands for this folder (next section) instead of "pass a build".

### Printing or running the build

Project detection (depth 2 from cwd, skipping `Pods/`, `node_modules/`, `*.xcodeproj/project.xcworkspace`, hidden folders): prefer `*.xcworkspace`, else `*.xcodeproj`. Covers `iosApp/` (KMP), `ios/` (Flutter `Runner.xcworkspace`, React Native), and plain Xcode repos.

Scheme, cheapest first:

1. **Read `xcshareddata/xcschemes/*.xcscheme` from disk** (instant, no package resolution). In each, the `LaunchAction` `BuildableReference` carries `BuildableName = "Kuokka.app"` [verified on `HackerNewsKMP.xcscheme`]; take the scheme whose launch product ends `.app` (not `.appex`, not `.xctest`). That gives both the scheme name and the product name (the file to look for afterwards).
2. If the project has no shared scheme (CrossfitTracker: `xcodebuild -list` shows the auto-created scheme `Crossfit Tracker`), run `xcodebuild -list -json` and say first: "Asking Xcode for your schemes. It may download your Swift packages (up to a few minutes)." Output shape [verified on two projects]: `{"project": {"configurations": [...], "name": "...", "schemes": [...], "targets": [...]}}` (a workspace gives `{"workspace": {"name", "schemes"}}`). The list contains noise: package schemes (`RevenueCatUI`, `RevenueCatUITests`), duplicates (`"HackerNewsKMP (Kuokka project)"` twice), extensions, UI tests. Rule: scheme equal to the project name, else the only scheme left after removing names ending `Tests`/`Extension`/`UITests` and names that are not in `targets`; else ask the user to pick from the list.
3. To learn the exact output path for a scheme: `xcodebuild -showBuildSettings -json -scheme S -sdk iphonesimulator -configuration Debug` returns a list of `{target, action, buildSettings}`; the app entry has `PRODUCT_TYPE = com.apple.product-type.application`, `TARGET_BUILD_DIR`, `FULL_PRODUCT_NAME`, `PRODUCT_BUNDLE_IDENTIFIER` [verified: `.../Debug-iphonesimulator`, `Crossfit Tracker.app`]. Only needed when not building into our own folder.

The command (print it, and run it with `init --build`):

```
xcodebuild -workspace App.xcworkspace -scheme App -configuration Debug \
  -destination 'generic/platform=iOS Simulator' -derivedDataPath .shotfleet/build build
# app: .shotfleet/build/Build/Products/Debug-iphonesimulator/App.app
```

`-derivedDataPath`, `-sdk`, `-showBuildSettings`, `-list -json`, `-skipMacroValidation`, `-skipPackagePluginValidation` all exist in this Mac's `xcodebuild -help` (Xcode 27.0) [verified]. `-destination 'generic/platform=iOS Simulator'` is standard Xcode syntax but I did not run a build [unverified here]; `-sdk iphonesimulator -configuration Debug` (README today) is the verified-by-help alternative. If the build fails with a "macro/plugin must be enabled" error, the hint is to re-run with the two skip flags (another session on this Mac passes them for CrossfitTracker); do not add them by default, they skip a security prompt.

Own `-derivedDataPath .shotfleet/build` means `init --build` finds the `.app` at a known path, ignores DerivedData volatility, and `init` should append `.shotfleet/` to `.gitignore` after asking. Builds take minutes: print "Building (this takes a few minutes, output in .shotfleet/build.log)" and stream only the last line.

Android: `./gradlew assembleDebug` (no module name: builds every application module, including Wear; the badging filter above picks the phone APK). Needs a JDK 17+: run it with `tool_env()`. If `gradlew` is missing, say "no gradlew here; run your build from Android Studio, then run `shotfleet init` again".

`init` flow, in order: discover, if none and `--build` run the builds, if none and no `--build` print the commands and "run `shotfleet init --build` to do this for you". Pass explicit paths exactly as today (arguments still win).

## 3. Starter flow that reads the app (`init --peek`, optional)

Today's `FLOW_TEMPLATE` is generic. What can be learned **without booting anything** is little (bundle id, app name, languages); a heuristic over all translations (short capitalised strings) is noisy. The valuable, still simple version uses what shotfleet already has:

1. Boot one device (iOS: `make_pool(1, ...)`; Android: first emulator of the pool), install, launch (`simctl launch` / `adb shell monkey -p <pkg> 1`), wait 5 s, take one screenshot (`simctl io <udid> screenshot` / `adb exec-out screencap -p`).
2. Run the existing OCR helper on it; normalise each line with `norm()`; keep lines that exactly equal a string in the app's English table (`by_text` in `translate_flow`). Those are real, tappable labels that shotfleet can translate: the flow can never start with a selector that fails on exactness (the number one first-flow failure).
3. Write the flow with the visible labels as commented suggestions, and keep `01_home`:

```yaml
- launchApp
- waitForAnimationToEnd:
    timeout: 5000
- takeScreenshot: 01_home
# Visible on your first screen (taken from your app's own strings):
# - tapOn: "Get Started"
# - tapOn: "Sign in"
# Add steps below, then a takeScreenshot: 02_<name> after each one.
```

Cost: one simulator boot (about a minute; an Android emulator first boot is longer), so it is opt-in (`init --peek`) and asked on a TTY ("Take a first screenshot to suggest steps? takes about a minute [y/N]"); off in CI. About 4 hours. The OCR compile happens here once, which doubles as the warm-up in section 5.

## 4. Android SDK, emulator, AVD

What shotfleet does today [verified in `android_pool`]: the AVD `shotfleet_android` is created on first `run` with `avdmanager create avd -n shotfleet_android -k system-images;android-36;google_apis;arm64-v8a -d pixel_5` and its `config.ini` is patched to 1080x1920 at 420 dpi (this Mac's AVD matches: `hw.device.name=pixel_5`, `image.sysdir.1=system-images/android-36/google_apis/arm64-v8a/`, `PlayStore.enabled=no`). If the image is missing it fails with "Install that system image in Android Studio's SDK Manager". `SDK` is `ANDROID_HOME` or `~/Library/Android/sdk`.

Gaps and fixes:

1. **SDK discovery.** `find_sdk()`: `ANDROID_HOME`, `ANDROID_SDK_ROOT`, `~/Library/Android/sdk`, `/opt/homebrew/share/android-commandlinetools` (the root of `brew install --cask android-commandlinetools`, whose caveat says "Default Android SDK root is /opt/homebrew/share/android-commandlinetools" [verified: `brew info --cask`]). First one with a `cmdline-tools/latest/bin` or an `emulator` folder wins. No `export` for the buyer.
2. **Use any installed image first.** Scan `<sdk>/system-images/android-*/google_apis*/arm64-v8a` and pick the newest API at or above 33 (per-app languages need 33+, README Limits); only fall back to `system-images;android-36;google_apis;arm64-v8a`. Most Android developers already have one, so no download.
3. **Exact commands in doctor** (package ids verified against `sdkmanager --list` on this Mac today: `emulator`, `platform-tools`, `build-tools;36.0.0`, `system-images;android-{33,34,35,36};google_apis;arm64-v8a`, `cmdline-tools;latest`):

```
# no SDK at all (needs Java; shotfleet finds it)
brew install --cask android-commandlinetools
yes | /opt/homebrew/share/android-commandlinetools/cmdline-tools/latest/bin/sdkmanager --licenses
/opt/homebrew/share/android-commandlinetools/cmdline-tools/latest/bin/sdkmanager \
  "platform-tools" "emulator" "build-tools;36.0.0" "system-images;android-36;google_apis;arm64-v8a"
# SDK present, only the image missing
~/Library/Android/sdk/cmdline-tools/latest/bin/sdkmanager "system-images;android-36;google_apis;arm64-v8a"
```

   When Java is keg-only the printed command needs `JAVA_HOME="..." ` in front; doctor prints it with the path it found. `avdmanager` needs no manual call: shotfleet creates the AVD. The download is large (the system image is the bulk; I did not measure it) so the `--fix` prompt says "large download" rather than a number.
4. **Doctor checks to add:** emulator binary, `adb` (from `<sdk>/platform-tools` as well as PATH), `aapt2` in `build-tools/*`, `avdmanager`, an installed image API 33+ arm64, and whether `shotfleet_android` exists ("will be created on first run").
5. The error in `android_pool` should reuse the same text ("Install it with: ...") instead of pointing at Android Studio.

## 5. First OCR compile (30 s to minutes)

Facts [verified: PLAN.md line 70, `ocr_tool`, `cmd_check`]: macOS compiles its text-recognition model once per helper binary; measured 127 s on a loaded Mac, 30 s on a quiet one, 3.5 s afterwards; the release binary runs the helper from `~/Library/Caches/shotfleet/ocr-<hash>` so it compiles once per install (this Mac has `ocr-c0f20f41983a`).

Changes, in order of value:

1. **Say it before, not after.** In `cmd_check` (and wherever the first OCR happens) print before the first call: `Preparing macOS text recognition for shotfleet. One-off: about 30 seconds, up to a few minutes on a busy Mac. Nothing is wrong if this is quiet.` Then a `.` heartbeat every 15 s. Keep the "prepared in Ns" line.
2. **Warm it up where the wait is free.** Start the first OCR call (a bundled 100x100 PNG with a few words, or any image) in a background thread at the start of `run`, so it overlaps simulator boot and the capture, which takes minutes anyway. The existing rule "one image alone first" stays in `check`; the warm-up must finish or be joined before the parallel reads. [unverified] that a read of a text-free or tiny image triggers the same compile as a real screenshot; measure it with a fresh copy of the helper on a quiet Mac before relying on it. If it does not, warm up with a real screenshot of the first locale as soon as it exists.
3. `doctor` reports `text recognition: ready` or `not prepared yet (first use takes about a minute)`, decided by whether `~/Library/Caches/shotfleet/ocr-<hash>` exists, and `doctor --fix` can prepare it.
4. `init --peek` (section 3) prepares it as a side effect.

## 6. One command from zero, honest prerequisites

Shortest honest list:

1. An Apple-silicon Mac with Homebrew (the formula is `arch: :arm64`, `:macos`).
2. Xcode from the App Store with an iOS Simulator runtime, for iOS. (`xcodebuild -downloadPlatform iOS` fetches the runtime; the flag exists [verified in `-help`], whether it asks for sudo is [unverified].) A fresh Xcode may need `sudo xcodebuild -runFirstLaunch` or one manual launch: doctor can only print this.
3. For Android: Android Studio, or just the command-line tools (section 4).
4. Your app must build in Debug (`init` finds the build or runs it).

Java and Maestro are not on the list: the formula brings them. Python and Swift are not needed (single binary).

## 7. Extensibility without default complexity

Principle: nothing here is on by default. A config with no extra tables behaves exactly as today. Everything is a TOML table plus a shell command, run by `/bin/sh -c` with `cwd` = the config's folder. No plugin API, no Python imports.

Two implementation notes that apply to all of it:

- `load_config` rejects unknown keys inside `[ios]`/`[android]` but does not look at other top-level tables, so a typo like `[hook]` would be ignored silently. Add a check: top-level tables must be in `{ios, android, hooks, overrides, check}` (and `devices` below), with the same "did you mean" message.
- `export` and a standalone `check` do not read the config today (`run.json` stores the app path only). Store the absolute config path in `run.json` (`"config": ...`) so those commands can find `[hooks]`. Hook output must go to **stderr** (`stdout=sys.stderr`): with `--json` stdout carries only the report, and `contextlib.redirect_stdout` does not cover child processes.

### Extension points

| Extension | Syntax | When it runs / what it changes | Environment passed | Default |
|---|---|---|---|---|
| **Hooks** | `[hooks]` keys `before_run`, `after_run`, `before_export`, `after_export`; value is a string or a list of strings (run in order) | `before_run`: before any device boots, after config checks. `after_run`: after capture and check. `before_export`: before files are copied. `after_export`: after the copy | see below | none |
| **Per-locale overrides** | `[overrides.<locale>]` with `"English text in flow.yaml" = "text in that language"` | Replaces the lookup for that selector in that language; silences the "untranslated" and "also means" warnings for it | none | none |
| **Custom checks** | `[[check.extra]]` with `name` and `run` | After the built-in checks; each stdout line `<locale>/<file>: <message>` becomes a problem (counts in exit code, blocks export of that locale) | `SHOTFLEET_OUT`, `SHOTFLEET_CHECK_DIR`, `SHOTFLEET_PLATFORM`, `SHOTFLEET_LOCALES`, `SHOTFLEET_CONFIG` | none |
| **Custom text reader** | `[check]` `reader = "python3 tools/ocr_tesseract.py"` | Same as env `SHOTFLEET_OCR` (env wins), but committed with the repo and used in CI | n/a | bundled macOS reader |
| **Custom device types** | `[[ios.extra]]` / `[[android.extra]]` tables, one more capture pass each into `<out>-<name>` | Same mechanism `ipad = true` already uses (a second `ios_run` with another prefix and out folder) | n/a | none |
| **Plugin discovery** | Unknown subcommand `shotfleet foo` runs `shotfleet-foo` from PATH (as git, gh and cargo do) | Only when the name is not a built-in command; `shotfleet --help` footer lists `shotfleet-*` found on PATH | same `SHOTFLEET_*` set, from the last run in `./out` or `--out` | no plugins |

### Hook events and environment variables

| Event | Extra variables | Non-zero exit |
|---|---|---|
| all | `SHOTFLEET_EVENT` (the event name), `SHOTFLEET_VERSION`, `SHOTFLEET_CONFIG` (absolute path), `SHOTFLEET_PLATFORM` (`ios` or `android`; `run` and `export` call the event once per platform section), `SHOTFLEET_OUT` (absolute output folder of that run), `SHOTFLEET_BUNDLE_ID` | see below |
| `before_run` | `SHOTFLEET_LOCALES` (the languages about to run) | aborts the run, exit 2: "hook before_run failed (exit 3): <command>" |
| `after_run` | `SHOTFLEET_LOCALES`, `SHOTFLEET_FAILED_LOCALES`, `SHOTFLEET_PROBLEMS` (count), `SHOTFLEET_EXIT` (shotfleet's own exit code, 0/1), `SHOTFLEET_REPORT` (`<out>/check.json`) | prints the failure and makes the final exit code 1, so CI notices a failed upload or notification |
| `before_export` | `SHOTFLEET_FASTLANE` (absolute path given to `--fastlane`), `SHOTFLEET_REPORT` | aborts the export, exit 2 (a gate: "do not export unless ...") |
| `after_export` | `SHOTFLEET_FASTLANE`, `SHOTFLEET_EXPORTED` (comma list of the listing folders written, e.g. `de-DE,fr-FR`), `SHOTFLEET_SKIPPED` (locales skipped for failed checks) | final exit code 1 |

`SHOTFLEET_OUT/run.json` and `check.json` already hold the details (screenshots, problems), so scripts can read them instead of new variables. No per-locale hook: iOS runs all languages in one sharded Maestro process and Android runs rounds of several languages, so a per-locale event has no honest meaning; use Maestro's own `runScript`/`runFlow` for in-app setup. Flags: `--no-hooks` skips all hooks (dry runs, debugging). Default timeout 600 s per hook, `hook_timeout_s = 1800` under `[hooks]` to change it. Hooks run only on commands the user typed; shotfleet never runs one on its own initiative. `--json` runs hooks too.

### Per-locale overrides: exact behaviour

```toml
[overrides.tr]                       # the locale as shotfleet names it (lproj / Android qualifier), e.g. tr, pt-BR, zh-Hans
"Next" = "İleri"                     # literal text; matched exactly like a translated label
"Advanced" = "re:Gelişmiş.*"         # prefix "re:" = regular expression (Maestro text selectors are regexes already)
"Search" = "Ara"                     # also fixes labels not in the app's strings (system UI, server text)
```

Implementation: `translate_flow(flow, base, target)` gets one more argument, `overrides` (dict English text to pattern). In `tr(raw)`, before `by_text.get(text)`: `if text in overrides: return yaml_single_quote(overrides[text])` (literal gets `regex_literal`, `re:` gets the rest as is). iOS passes `overrides[lp]`; the Android round function, which translates one flow for several languages at once, ORs the patterns of the languages in the round. About 8 lines plus config validation. This is the escape hatch for the collision warning ("`tr: 'Next' -> 'İleri' also means 'Advanced'`") that today can only be handled by editing the flow with `below:`.

Not proposed: whole-flow-per-locale files (`flow.de.yaml`): fine for iOS, but Android's shared-round design makes it a redesign. Revisit if a buyer asks.

### Custom checks: exact behaviour

```toml
[[check.extra]]
name = "no placeholder text"
run  = "python3 tools/no_lorem.py"      # prints lines like:  de/02_settings.png: contains "Lorem"
```

Each non-empty stdout line must start with `<locale>/` (the same shape as built-in problems, so `cmd_export`'s existing `p.split(":")[0].split("/")[0]` marks that locale as bad and skips it). Lines not in that shape are shown but treated as notes, not problems. Non-zero exit of the script itself is a setup error (exit 2), not a problem.

### Custom device types

```toml
[[ios.extra]]
name = "se"                          # output goes to out-se/, like out-ipad for ipad = true
device_type = "com.apple.CoreSimulator.SimDeviceType.iPhone-SE-3rd-generation"

[[android.extra]]
name = "tablet10"
avd = "shotfleet_tablet10"           # created like shotfleet_android is
system_image = "system-images;android-36;google_apis;arm64-v8a"
device = "pixel_tablet"              # avdmanager -d
```

Valid keys inside an entry: the same as the section's own keys minus `app`/`apk`/`flow`/`out`. Export of the Android extras needs fastlane supply's per-device folder names (`sevenInchScreenshots`, `tenInchScreenshots`); that mapping is the real work, so ship the iOS case first or only the capture side. Play tablet screenshots are not supported today (README).

### Plugin discovery: exact behaviour

In `main()` before argparse: `if len(argv) > 1 and argv[1] not in COMMANDS and (exe := shutil.which("shotfleet-" + argv[1])): os.execv(exe, [exe, *argv[2:]])`, with `SHOTFLEET_OUT`/`SHOTFLEET_CONFIG` exported when `./shotfleet.toml` exists. Five lines, no registry, nothing to learn unless you write one. A hook can call the same executable (`after_export = "shotfleet-upload"`).

### Three real use cases

**A. Upload with fastlane after export.** (`screenshots_path` and `skip_binary_upload`, `skip_metadata`, `overwrite_screenshots` are deliver options; verified against docs.fastlane.tools/actions/deliver. App Store Connect auth stays in fastlane: `FASTLANE_*` env or `api_key_path`.)

```toml
[hooks]
after_export = '''
case "$SHOTFLEET_PLATFORM" in
  ios) fastlane deliver --skip_binary_upload --skip_metadata --overwrite_screenshots \
         --screenshots_path "$SHOTFLEET_FASTLANE/screenshots" ;;
  android) fastlane supply --skip_upload_apk --skip_upload_aab --skip_upload_metadata \
         --skip_upload_changelogs --skip_upload_images --metadata_path "$SHOTFLEET_FASTLANE/metadata/android" ;;
esac
'''
```

Use `before_export` with a prompt script (`[ -t 0 ] && read -p "Upload? [y/N]" a && [ "$a" = y ]`) if the upload must stay a deliberate human step. The Android `supply` flags mirror the README's existing manual command; I did not re-verify supply's option names (`metadata_path` in particular) against its docs.

**B. Frame with frameit.** Frames must be added after export, because `cmd_export` copies every `*.png` in `raw/<locale>/`, so framing in place would export both versions. frameit takes `path:` (docs.fastlane.tools/actions/frameit [verified]) and needs a `Framefile.json` in that folder.

```toml
[hooks]
after_export = 'fastlane run frameit path:"$SHOTFLEET_FASTLANE/screenshots"'
# then the README's step: shotfleet check fastlane/ --app MyApp.app   (flags a translated caption over an app that isn't in that language)
```

Caveat to state in the docs: frameit's documented device frames stop around the iPhone 11 / XS Max generation, so it may not have a frame for a 6.9" iPhone 17 Pro Max screenshot [unverified; docs list no current models]. The same hook works with any tool that takes a folder (ButterKit, AppScreens CLI) by swapping the command.

**C. Post a Slack message.** Slack incoming webhooks take a JSON body with a `text` field (api.slack.com/messaging/webhooks; not re-fetched today). The webhook URL stays in the environment, never in the repo.

```toml
[hooks]
after_run = '''
curl -sS -X POST -H 'Content-type: application/json' "$SLACK_WEBHOOK_URL" \
  --data "{\"text\":\"shotfleet $SHOTFLEET_PLATFORM: $SHOTFLEET_PROBLEMS problem(s), failed: ${SHOTFLEET_FAILED_LOCALES:-none}\"}"
'''
```
