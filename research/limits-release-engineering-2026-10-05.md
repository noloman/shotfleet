## Top 3 findings

1. **The release process builds, then ships different bytes than it tested, and keeps no copy of what it shipped.** VERIFIED: `packaging/release.sh` builds and deploys in one run, and `packaging/go-live.sh` calls it, so "test those exact files, then go-live" (STATUS.md, "How to release again") cannot hold: `research/go-live-gate.md` G4 says "go-live.sh rebuilds through release.sh, so the shipped files get new hashes" (tested build 9,732,997 bytes, sha256 079233aa...; shipped archive 9,731,376 bytes, sha256 8b36c7f8...; G3's 65/65 fixture run was on the earlier build, G10 verified the shipped one by smoke and by hand). `packaging/build.sh` starts with `rm -rf build dist`, and `site/public/download/` is gitignored (`.gitignore`), so the shipped 0.1.0 tarball and package exist only inside Cloudflare's deployment. I found no copy: the main checkout has `dist/shotfleet-0.1.0-macos-arm64.tar.gz` of 8.7 MB (the published one is 9.7 MB), `site/public/download/` does not exist in the main checkout, and a search of `/Users/manu/Developer` and `/private/tmp` (depth 6) found only the 0.1.1 session's own test copies. INFERENCE with a cheap test: any site-only `wrangler deploy` from a checkout that lacks `site/public/download/` (the main checkout is one; other sessions deploy the site, `research/go-live-gate.md` rollback section) publishes a version without `/download/*`, because a Workers static-assets deploy uploads the directory and deletes assets that are no longer in it ([workers-sdk issue 3382](https://github.com/cloudflare/workers-sdk/issues/3382), search summary, undated). That would make `install.sh` answer 404 for every new buyer until someone rebuilds. Rollback is also stale: G11 and its "Rollback" section name the waitlist version `5716b430-...` as the target; after go-live that target would put the waitlist back, and the version ID of the live 0.1.0 deployment is written nowhere in the repo. G11 says "written and rehearsed" and the Result says only "written below": nothing was rehearsed.
2. **A 0.1.0 buyer has no reliable way to learn that 0.1.1 exists, and the docs do not say how to update.** VERIFIED: the only notice is one line in `shotfleet doctor` (`shotfleet.py` lines 2616-2621 and 2990-2991, same in the 0.1.0 build 081853b), fetched with `urllib.request.urlopen(url, timeout=5)` and no `context=`, while every other download uses `tls_context()` (certifi). Any error is swallowed (`except OSError`). The 0.1.0 frozen program is built from Homebrew's Python, whose OpenSSL looks for its CA file in `/opt/homebrew/etc/openssl@3/cert.pem` (measured on this Mac: `ssl.get_default_verify_paths()`); PyInstaller's certifi runtime hook is not in the bundle (name list of `pyi_rth_*` in `dist/shotfleet/shotfleet`: inspect, pkgutil, multiprocessing). INFERENCE: on a Mac without Homebrew the request fails certificate verification and `doctor` stays silent, so 0.1.0 buyers without Homebrew never see the notice (test: run the 0.1.0 `doctor` with Homebrew hidden, the `sandbox-exec` method `STATUS.md` row D1 already used). The 0.1.1 standalone Python reads `/private/etc/ssl/cert.pem` (measured, file exists on this Mac; stock macOS ships it, INFERENCE), so 0.1.1 and later probably work. README and `site/public/docs.html` contain no instruction to update (grep for "update" finds only the licence sentence), and the privacy page and a claim promise `doctor` is the only command that asks the site for the version (`tests/claims.json` line 66, 1555), so the notice cannot be moved to `run`. The reliable channel is an email to buyers through Gumroad (OWNER, section 2).
3. **Build inputs and the notarization credential are single points of failure that nothing checks before a release starts.** VERIFIED: `packaging/build.sh` runs `pip install --upgrade pyinstaller certifi` (unpinned, network); `release.sh` and `go-live.sh` run `npx --yes wrangler@latest deploy` (unpinned, and `site/` has no `package.json`); Python is whatever `python3` is (Homebrew, measured 3.14.8 against a build that said 3.14.2 earlier, `limits-platform-reach` note); the 0.1.1 session had to rebuild offline with `PIP_NO_INDEX=1` and a `.pth` shim to make PyInstaller 6.22.3 and certifi 2026.6.17 appear (`/Users/manu/Developer/shotfleet-rc-build/0.1.1/tools-stage/python-wrapper.sh`). The notarytool profile `KeysiNotary` lives in one login keychain; it vanished once (2026-10-03, recreated 2026-10-04, `STATUS.md` line 18) and `go-live.sh --dry-run` does not check it (it prints "not checked here", line 56). When it is missing, `build.sh` fails late, after signing, with a message that points at a log id that does not exist (the pipeline `notarytool ... | tee` hides the exit status; the next line prints "see xcrun notarytool log <id>", `build.sh` line 41). Cost to fix: a preflight script, a hashed requirements file, a pinned wrangler and a written recovery (section 3).

## 1. Reproducible build: what makes two builds of one commit differ

**Evidence that it happens.** VERIFIED: the tested build and the shipped build of the same code differ by 1,621 bytes and in hash (finding 1; the go-live commit that sets `GUMROAD_PRODUCT_ID` is one line, so the difference is not the source). Nobody can say today which of the causes below produced it.

| Source of difference | State | Evidence |
|---|---|---|
| `pip install --upgrade pyinstaller certifi` at build time | unpinned, network | `packaging/build.sh` line 17. certifi's bundle changes with every release, PyInstaller changes its bootloader and hooks; the 0.1.1 build log prints "PyInstaller: 6.22.3, contrib hooks: 2026.8" |
| Python | floats (`python3`) | Homebrew moved from 3.14.2 to 3.14.8 between builds (`limits-platform-reach` note); `build.sh` itself says its venv's Python "may be gone (brew upgrade)". Homebrew's Python is also built for the host macOS (minimum 27.0 measured, same note) |
| Swift compiler and SDK | host Xcode | `swiftc -O ocr.swift` has no `-target` on main, so the helper's minimum macOS and Swift runtime imports follow the Xcode in use. The 0.1.1 branch adds `-target arm64-apple-macos13.0` (diff of its `build.sh`, VERIFIED) |
| Python hash randomisation in PyInstaller output | not controlled | PyInstaller documents that two builds of the same source can differ because Python randomises hashing, and that setting `PYTHONHASHSEED` to a fixed integer makes bundles identical ([PyInstaller, Advanced Topics](https://pyinstaller.org/en/stable/advanced-topics.html), read 2026-10-05). A third-party report says `PYTHONHASHSEED=0` alone fixed it on macOS and `SOURCE_DATE_EPOCH` alone did not ([mfeminer/lane PR 26](https://github.com/mfeminer/lane/pull/26) through a search summary; [PyInstaller issue 4972](https://github.com/pyinstaller/pyinstaller/issues/4972), title and first post only). `SOURCE_DATE_EPOCH` in PyInstaller is documented for Windows PE headers, from 4.8 |
| Tarball bytes | file mtimes and the gzip header | `tar -C dist -czf ...` (`build.sh` line 36). INFERENCE: tar stores each file's mtime and gzip stores a time and a name, so the same tree packed twice can differ. `SOURCE_DATE_EPOCH` is the standard way to fix timestamps ([reproducible-builds.org](https://reproducible-builds.org/docs/source-date-epoch/)); test: pack one folder twice a second apart and compare |
| Code signature | differs by design | every `codesign --timestamp` embeds a time stamp from Apple's server, and notarization requires the secure timestamp (Apple developer forum thread 666714, search summary). So the signed Mach-O files, the tarball and the package cannot be bit-identical across builds. The package signature and the notary ticket differ too (`pkgbuild --timestamp`, `stapler`) |
| Notarization ticket | per submission | each build is a new submission (IDs in G4: 008b9344..., a7c22d9e...) |
| Build host | one Mac, other sessions loading it | not an input, but `build/` and `dist/` are shared paths wiped by `rm -rf build dist` |

**What "re-buildable and verifiable by a second session" can mean.** Bit-identical signed output is not reachable; the claim to aim for is: *a second session, given the commit and the release record, rebuilds with the same inputs, strips the signatures, and gets identical unsigned content*. Pins and checks:

1. **Release record**, one file per release, committed: commit hash, tool versions (`xcodebuild -version`, `swiftc --version`, Python build and its tag and SHA-256, PyInstaller, hooks-contrib, certifi), `PYTHONHASHSEED` and `SOURCE_DATE_EPOCH` used, SHA-256 and size of the tarball and the package, the two notary submission IDs, the Cloudflare version ID, the macOS minimum measured by `tools/macho-minos.py`. Today these live as prose in `research/go-live-gate.md` (and the tarball hash is shortened there to `8b36c7f8...6218`).
2. **Pinned inputs:** `requirements-build.txt` with `==` versions and hashes and `pip install --require-hashes` (pip's hash-checking mode; nothing in this note ran pip, the hashes still have to be produced once); one Python (python-build-standalone, `uv python find 3.14 --managed-python`, tag recorded; the 0.1.1 session's wrapper hard-codes `/Users/manu/.local/share/uv/python/cpython-3.14.2-macos-aarch64-none/bin/python3.14`, which only exists on this Mac); `swiftc -target`; `PYTHONHASHSEED=1` and a fixed `SOURCE_DATE_EPOCH` exported by `build.sh`; `gzip -n` or a normalised mtime for the tarball.
3. **Checks a second session can run, in order of cost:** (a) `tools/verify-release.sh` on the published files: checksum, signature, team ID, hardened runtime, quarantined run, `macho-minos`, the package's `spctl` and `stapler`, version (item 8). (b) A second unsigned build with the same pins; compare the file list, sizes and SHA-256 of every non-Mach-O file, and of every Mach-O file after `codesign --remove-signature` on a copy. Not run: this needs two builds and PyInstaller's behaviour on macOS with a fixed seed is only second-hand. Experiment for after the 0.1.1 gate: two unsigned builds back to back with and without `PYTHONHASHSEED`, diff, about 5 minutes of build time, no devices.
4. **What not to promise:** "reproducible" in public text. Say "built from commit X with pinned tools, hashes published".

## 2. The update path

**What exists today (VERIFIED).**
- `install.sh` is also the updater: it downloads the tarball and checksum, unpacks to a temp folder, then `rm -rf "$APP"` and moves the new folder into `~/Library/Application Support/shotfleet/app` and relinks. The licence file is a sibling (`LICENCE_FILE = ~/Library/Application Support/shotfleet/licence.json`, `shotfleet.py` line 3751), so an update keeps the activation. STATUS row 6 records the update-over-an-installed-copy case working (2026-10-02, local server). The removal and the move are two steps, not one atomic rename.
- The installer package lays files under `/usr/local/lib/shotfleet` with a postinstall that links `/usr/local/bin/shotfleet`; there is no preinstall, so INFERENCE: installing a newer package over an older one overlays files and leaves stale ones (for example Homebrew-Python libraries from 0.1.0 next to the standalone `libpython` of 0.1.1). VERIFIED: `packaging/pkg.sh` creates only a `postinstall` script. Test: install 0.1.0 then 0.1.1 packages and compare the folder with the 0.1.1 tarball; it needs the owner's administrator password.
- `install.sh` links into the first writable of `/opt/homebrew/bin`, `/usr/local/bin`, `~/.local/bin`; the package links into `/usr/local/bin`. A buyer with both can run an old copy first on the PATH (INFERENCE, depends on PATH order; `which -a shotfleet` shows it).
- `doctor` prints "shotfleet X is out (you have Y): curl -fsSL https://shotfleet.com/install.sh | sh" when `/download/VERSION` is newer. Finding 2 says why that probably does not reach 0.1.0 buyers without Homebrew.
- No `shotfleet update` command. `--version` and every other command make no network call (claim, `STATUS.md` and the privacy page).
- The privacy page already names the one site request: "`shotfleet doctor` also asks this site for the latest version number; that is an ordinary page request and I don't record it" (`site/public/privacy.html`). The terms say "A year of updates is included" and the program has no date logic (grep in `shotfleet.py` finds no purchase-date check), so an update path must not enforce the year.

**What a safe `shotfleet update` (or a better notice) would need.**
- Same-origin checksum is not authentication: `install.sh` fetches the tarball and its `.sha256` from the same host, so the checksum catches truncation and corruption, not a compromised host or Cloudflare account. The strong check that costs nothing to build is Apple's own: after download, `codesign --verify --deep --strict` plus a requirement on the team ID (`codesign -R=...` with `certificate leaf[subject.OU] = "2357A78TMR"`; exact syntax to be tested), offline, with tools on every Mac. A file fetched by Python or `curl` carries no quarantine flag, so Gatekeeper and the notarization ticket are not consulted (VERIFIED: G7 "no quarantine flag"; `build.sh` comments), so the signature check has to be done by the program or the script.
- Extract beside the target, verify, swap with two renames, keep the old folder until the new one runs `--version`, restore on failure. Refuse on a package install (root-owned folder) and print the package or `install.sh` instruction.
- A new `urlopen` call site: the AST test `G1NothingLeavesTheMac` (claims line 66) lists allowed call sites and hosts; the claim text, the privacy sentence ("`shotfleet update` downloads the release archive from this site when you run it; the request carries Python's user agent and your IP address, nothing else") and the claim that `doctor` being the only command that asks the site must change together.
- Cost M, value low while `curl ... | sh` already works and costs the buyer one line. Leave it until a buyer asks or three releases have shipped. What is cheap: tell people the one line (docs, receipt, email) and make the notice dependable (item 11).

**Gumroad update email (OWNER).** Gumroad's Help Center says a seller sends an email from the Emails dashboard ("New email"), and can narrow the audience to customers of a given product and a date range; workflows can send automated emails on a trigger such as a purchase ([Send email updates](https://gumroad.com/help/article/169-how-to-send-an-update), [Workflows](https://gumroad.com/help/article/131-using-workflows-to-send-automated-updates); I could only read search-result summaries on 2026-10-05, the pages themselves returned little). Not checked: per-email limits or cost, whether Gumroad emails are rate limited, and whether the product's receipt text can carry an "how to update" line. A suggested message after the 0.1.1 deploy: what changed in two or three lines, the update command, "your licence stays". Claude drafts, Manu sends; Claude posts nothing. A second use: put "To update later: run the install line again" in the Gumroad receipt or product content page so the instruction sits where the buyer's key sits.

## 3. Notarization automation and the `KeysiNotary` credential

**What exists (VERIFIED).** `release.sh` defaults `NOTARY_PROFILE=KeysiNotary`; `build.sh` submits a zip with `xcrun notarytool submit --keychain-profile ... --wait`, then runs a quarantined copy of the tarball; `pkg.sh` submits the package, staples it, then `spctl --assess --type install`. `store-credentials` saves credentials in the default login keychain, with `--keychain` for another keychain and `--sync` for iCloud Keychain; by default it validates them before saving ([notarytool man page mirror](https://keith.github.io/xcode-man-pages/notarytool.1.html), read 2026-10-05). The app-specific password is named `shotfleet-notary` (`docs/owner-checklist-kvk-and-tax.md` line 35). Certificates (read from the keychain today, public data): Developer ID Application expires 2031-09-11, Developer ID Installer 2031-09-17. `LAUNCH.md` lines 50-53 hold a one-line recovery ("xcrun notarytool store-credentials KeysiNotary").

**What broke and what breaks.** The profile vanished once; the repo records no cause. Candidates (INFERENCE, none tested): a login-keychain reset or restore, a macOS upgrade, another process or user session removing it on this shared Mac. A different failure is an app-specific password that exists in the keychain but is rejected: Apple revokes all app-specific passwords when the Apple Account password is changed ([Apple Support 102654](https://support.apple.com/en-us/102654), through a search summary on 2026-10-05). The symptoms differ: a missing item errors at once, a revoked password errors at the first Apple call (HTTP 401 style). When it happens in the middle of `build.sh`: signing is already done, the notary step fails after up to 148 s of build, and `build.sh` line 41's message ("xcrun notarytool log <id> ...") names an id that was never created (the exit status of `notarytool ... | tee` is lost, then `grep -q "status: Accepted"` fails). Nobody can sign, notarize or staple without Manu's Mac and keychain; a second session can only verify.

**Documented recovery (owner steps; Claude does not enter credentials).**
1. Confirm: `xcrun notarytool history --keychain-profile KeysiNotary` (read only, needs the network). A missing profile and a rejected password print different errors; keep the text.
2. Recreate the app-specific password at account.apple.com (Sign-In and Security, App-Specific Passwords), name it `shotfleet-notary`, put it in the password manager.
3. `xcrun notarytool store-credentials KeysiNotary --apple-id <Apple ID> --team-id 2357A78TMR` (it prompts for the password; do not paste it into a shell line or a chat), accept the validation step.
4. Re-run step 1. Then `tools/release-preflight.sh` (item 5) before any release.
5. Never run a release build until step 4 passes; never put the password in the repo, an environment file or a session transcript.

**App Store Connect API keys instead of the app-specific password?**
- VERIFIED (Apple, [App Store Connect API help](https://developer.apple.com/help/app-store-connect/get-started/app-store-connect-api/), read 2026-10-05): only the Account Holder can request API access, reviewed case by case; team keys are generated by the Account Holder or an Admin; several team keys can be active; a revoked key cannot be reinstated and shows for 30 days; the page names no cost. `notarytool store-credentials` takes `--key`, `--key-id` and `--issuer` for an API key, and for a key file the man page says the key's contents are stored in the keychain item so the file can be deleted (man page above). Apple's other documented path, the app-specific password, is the one in use.
- Not verified: the role a team key needs for notarization (to be found by trying `notarytool history` with a key made with the least role), whether the `.p8` can be downloaded only once (general knowledge), and the membership fee (nothing in the pages read states a price for keys; the Developer Program fee is already paid for the certificates).
- Assessment (INFERENCE): a team key does not depend on the Apple Account password, can be revoked and replaced without 2FA prompts and can be a second profile (`KeysiNotary-api`) next to the first. It is stored in the same kind of keychain item, so it does not stop the item from vanishing; the protection is a backup of the `.p8` and the Key ID and Issuer ID in the owner's password manager and the preflight check. Owner: Manu (the Account Holder of team 2357A78TMR, INFERENCE from the certificate subject). Cost: none beyond ten minutes. Recommendation: create one team key, store it as a second profile, keep the app-specific password as the fallback.
