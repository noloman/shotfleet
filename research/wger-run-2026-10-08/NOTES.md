# wger run record, 2026-10-08

shotfleet 0.1.6 on wger 2.1.1 (tag 2.1.1, commit cf12708, debug builds): iPhone (3 runs, 36 screenshots) and Android (2 runs, 36 screenshots). This file merges the iPhone notes and the Android notes of the run (both written by the runner, then corrected where noted). The numbers come from the run.json and check.json files in the sub-folders. No frames (PNG) and no .app or .apk are kept here; they stay in the build folder `/Users/manu/Developer/shotfleet-rc-build/showcase-wger/` (out-iphone-run1..3, out-android-run1..2).

## What ran

- App: wger, an open-source Flutter workout app (github.com/wger-project/flutter), AGPL-3.0-or-later with an app-store exception. Version 2.1.1 build 280, **built from tag 2.1.1** = commit cf1270845e1843dfa77784153b4a571126e4023f (`cf12708`). The repo HEAD (`57d2ee4`, two commits later) was tried first for Android and did not build (see finding e), so both platforms use the tag.
- Builds, all **debug** builds, compiled by me: Flutter 3.47.6 stable, Dart 3.13.5, Xcode 27.0. iPhone: `flutter build ios --simulator --debug` (Runner.app, bundle id de.wger.flutter.community, 150 s). Android: `flutter build apk --debug` (package de.wger.flutter.debug, 150 s on the second try). No release build was possible: the release signing key in the repo exists only as a gpg-encrypted file. No tracked file was edited.
- Tool: shotfleet 0.1.6 (released binary), Maestro 2.0.10. Devices: iPhone, one iPhone 17 Pro Max simulator, iOS 26.4, `parallel = 1`; Android, one emulator (shotfleet's own AVD `shotfleet_android`, 1080x1920, Android 16), `parallel = 1`. Translations: shotfleet read the app's own `lib/l10n/*.arb` files through `strings =` in the toml, because Flutter keeps its translations in compiled code.
- Languages: ar, de, es, fr, hr, uk (ar is right to left).
- Screens (the ones reachable without an account): 01 login, 02 Advanced sheet, 03 Self-hosted, 04 token login, 05 Register, 06 Register errors (Register pressed with empty fields; the form stops at validation, no request). **Never done: login, sending credentials, registering an account.** The "Other sign-in options" link and the Log in button are never tapped.
- Both platforms show the red **DEBUG banner** (top right, top left in Arabic).
- The debug build pre-fills the login form with the project's published test user `user` and a masked password. That is the app's own default, shotfleet typed nothing. It is visible on frame 01 only; the Register switch clears the fields. Nothing else private is in any frame.
- No network capture was run. "No network call" rests on reading the app source (`AuthNotifier._tryAutoLogin`, `AuthCard._submit`) and the frames.

### Check results and the evidence difference

- iPhone: `shotfleet check` read the **view hierarchy** (`evidence: "hierarchy"` in every row). 0 problems.
- Android: Maestro 2.0.10 keeps no per-step hierarchy on Android, so shotfleet read the pictures by **text recognition** (`evidence: "ocr"` in every row, macOS Vision). 0 problems, but this is weaker evidence than the iPhone one. I therefore looked at every frame myself.
- Both checks ran as `shotfleet check <run> --strings "lib/l10n/*.arb"`. The `check-in-run.json` files are the checks shotfleet ran inside each run.
- A green check does not prove that every tap hit the right button; it shows that the screens carry the right language.

## What went wrong before the runs that count

1. iPhone dry attempt 1 (rc 1, 313 s, 0/6): Maestro "iOS driver not ready in time" on the first boot of the pool simulator, then `simctl uninstall` did not answer within 60 s. Load was 13 at the start. Retried unchanged.
2. iPhone dry attempt 2 (rc 1, 5/6, 128 s): shotfleet itself replaced the stuck pool simulator `shotfleet-1` with a new one. Step 06 failed my own assert (I had asserted an e-mail message that the app does not show for an empty e-mail field).
3. In that same attempt `01_login` was the **splash screen** (logo on grey) although the view hierarchy already listed "Log in". `check` would have passed it. I only saw it by looking at the frame. Fix: a real 6-second wait plus `waitForAnimationToEnd` before frame 01. The splash PNG stays in the build folder (`record/logs/failed-attempts/dry-failed-0921-01_login-SPLASH-frame.png`), not in this record.
4. iPhone dry attempt 3: 6/6, all six frames looked at. `flow.yaml` is the final flow used by dry, run1, run2 and run3. `flow.used-by-dry-attempts-1-2.yaml` is the earlier version, `flow.draft.yaml` the first draft.
5. `check --app` failed on both platforms (finding b). Logs in `logs/failed-attempts/` and `logs-android/failed-attempts-android/`.
6. Android: nothing went wrong in the flow or the runs; the same `flow.yaml` (as `flow.android.yaml`, one comment line added) worked. Two things needed care: the first Android build tried HEAD and failed (finding e), and `--platform android` needs `ANDROID_HOME` set.

## Findings for shotfleet

a. **First-frame splash screen got through.** A frame 01 was the splash screen while the hierarchy already listed "Log in", so `check` would have passed it. shotfleet took the shot before the first real frame. I found it only by looking at every frame. `waitForAnimationToEnd` and an `extendedWaitUntil notVisible` of a missing element both return at once on a static screen, so a real wait was needed.
b. **`check --app <Runner.app or APK>` fails on this Flutter app.** iPhone: exit 2, "Runner.app contains no translations shotfleet can read". Android: exit 1 and 0 screenshots checked ("the app has no <lang> translation, so this listing shows another language" for every language). Only `check <run> --strings "lib/l10n/*.arb"` works (also when `--app` is given in addition, the `--app` form still fails). The hint in the message does point at `strings`, but `--app` plus `--strings` is a natural thing to type.
c. **Maestro "iOS driver not ready in time"** on a simulator's first boot, with the machine at low load (13).
d. **shotfleet replaced its own stuck pool simulator** during the retry (the iOS 26.4 `shotfleet-1`). It worked, but the old one was gone afterwards.
e. **The HEAD of the wger repo did not build on Android**: a bump of the `html` package to 0.15.7 removed a method that flutter_html 3.0.0 uses (`matches`). The tag 2.1.1 builds. The maintainer (rolandgeider) wrote on discussions/1389 on 2026-10-08 (13:05Z) that it should work again, he hadn't pushed the fix yet, so the HEAD problem was only for that day. No release build is possible because the signing key is gpg-encrypted.
f. Earlier WOD findings: the `scrollUntilVisible` text form (the string form of `element` does not get translated in 0.1.6, so it is written as `{text: ...}`) and colliding texts (`.*Register` for the link, `Register` for the button) were written around in this flow from the start, so neither bit here. They were not re-found.
