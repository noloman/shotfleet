# Plan for shotfleet 0.1.2 (2026-10-05, written right after 0.1.1 went live)

Docs only. No code, packaging or site change is made by this note. Sources: `research/limits-release-engineering-2026-10-05.md`, `research/limits-platform-reach-2026-10-05.md`, `research/release-0.1.1-evidence-2026-10-05.md`, `docs/handoff.md` section 13, PR #44, and the coordinator's list of small fixes.

## What 0.1.1 left open (the reason for 0.1.2)

- **The release pipeline ships different bytes than it tests.** `packaging/release.sh` builds and deploys in one run, so the tested files and the shipped files differ (0.1.0: 1,621 bytes). 0.1.1 avoided this by hand (publish the tested files, record the live version first, deploy from a tree that holds `site/public/download`). That discipline lives in a scratch script and in people's heads.
- **0.1.0 buyers have no reliable way to learn that 0.1.1 exists.** Only `doctor` mentions a newer version, and nothing tells buyers how to update.
- **Build inputs are not pinned** (`pip install --upgrade pyinstaller certifi`, an unpinned Python); 0.1.1 was built offline through a wrapper.
- **Known small defects:** `--json` prints only the last report; an invalid `SHOTFLEET_KEY` silently runs 2 languages (the coordinator's list; draft PRs from the owner of that research are coming).
- **Features and guards waiting:** PR #44 (Android screen text from the UI tree, conflicts with main now), and two guards from the platform-reach note (default iPhone device type falls back to the newest `iPhone N Pro Max`; refuse an Android image below API 33 before booting it).
- **Unproven:** starting on macOS 13 and 26.0 to 26.2, a clean Mac, a refunded key on the real API, and iOS 27 with several simulators (one simulator passed on a quiet Mac).

## Scope, in three groups

**A. Release pipeline (no device; do first, it protects everything after it).**

| # | Item | Cost | Risk |
|---|---|---|---|
| A1 | Split release into build (existing) and publish: publish takes already tested files, checks their SHA-256 against a recorded manifest, records the current live Cloudflare version id, refuses to deploy a site without `site/public/download` or with a `VERSION` that differs from the one named, deploys, verifies, rolls back on failure (the 0.1.1 deploy script is the working draft) | S | low; rehearse once on the throwaway worker `shotfleet-staging` |
| A2 | A read-only preflight before any release: signing identities and expiry, `notarytool history`, `wrangler whoami`, clean tree, free disk | XS | none |
| A3 | A verify-release script that does by hand today what G5 and the post-deploy checks do: checksum, `codesign --verify --deep --strict`, team id, hardened runtime, quarantined `--version`, `tools/macho-minos.py` with a failing maximum, `spctl` and `stapler` for the package | S | low |
| A4 | A test that `VERSION`, the top `CHANGELOG.md` heading and the docs page "Last checked" line agree (it caught a mismatch on 0.1.1) and that the macOS minimum measured by `tools/macho-minos.py` stays at 13.0 or below | S | low |
| A5 | Pinned build inputs: exact versions and hashes for PyInstaller, its hooks and certifi, and a recorded standalone Python (3.14.2 today), so no offline wrapper is needed | S | needs the packages downloaded once to produce the hashes (a download for Manu to approve: names, sources, sizes first) |
| A6 | Delete or fix stale files named in the release-engineering note (`shotfleet.spec`, `packaging/shotfleet.rb`) | XS | none |

**B. Code (needs a gate; unit tests first).**

| # | Item | Cost | Risk |
|---|---|---|---|
| B1 | `--json` prints every report, not only the last | XS | low |
| B2 | An invalid `SHOTFLEET_KEY` says so instead of silently running 2 languages | XS | low; touches the licence path, so re-test activation, refusal and the offline grace on the built binary |
| B3 | The two platform-reach guards (device type fallback, API 33 refusal), patch and tests exist in `research/proposed-platform-reach/` | S | low; the fallback is untested on an Xcode older than 26 |
| B4 | PR #44, Android text from the UI tree: rebase on main (one known conflicting hunk with the check-quality change), keep the blank-frame check and the hierarchy field, rerun | M | medium: it changes Android capture (a marker step after every screenshot, Maestro 2.7 or newer); it needs the Android fixture on Maestro 2.11.0 AND on 2.0.10 (the fallback) after the rebase |

**C. Owner items and unproven claims.**

- Gumroad email to 0.1.0 and 0.1.1 buyers with the one-line update command, and the same line in the docs (OWNER: the email).
- A macOS 13 or 26.0 to 26.2 start test needs a real Mac or a VM (no hosted runner); until then the public line stays "Built for macOS 13 or later on Apple silicon; tested on macOS 27."
- A refunded key on the real Gumroad API needs a paid sale by a second person.

## Device slots (under the lock in `docs/device-queue.md`)

1. B4 only: Android fixture e2e on Maestro 2.11.0, then on 2.0.10, one emulator on a quiet Mac, about 45 minutes.
2. The release gate on the final signed build: iPhone (iOS 26.4 pinned) plus iPad plus Android fixture e2e, 40 to 55 minutes (0.1.1 took 55 under heavy load; do it on a quiet Mac).
3. Optional, same slot or after: one simulator, one language on iOS 27 with the final build, about 20 minutes.

## Recommended order

1. **A1 to A4 and A6 first, no device**, rehearsed on `shotfleet-staging`. The pipeline is then ready before the code is.
2. **A5** once Manu approves the downloads (or keep the documented offline wrapper for one more release).
3. **B1 to B3** with unit tests, one full gate.
4. **B4**: rebase, unit tests, device slot 1. If the Android e2e fails on 2.0.10, ship 0.1.2 without B4 and keep B4 for 0.1.3.
5. **Build** with the pinned inputs, run A3 on the result, **device slot 2** (and 3 if time), then publish through A1, verify, tell the owner so the email can go.

## Estimate and risks

About a day and a half of agent time plus two device slots, and one hour of gate waiting on a loaded Mac. Main risks: (1) B2 and B4 touch the licence and capture paths, the two places where a wrong change costs buyers or sales, so each needs its own test and the full device gate; (2) a loaded or swapping Mac turns a 25 minute gate into 55 (0.1.1: swap 17 GB until idle build daemons were stopped), so check memory before the gate; (3) the standalone Python is 3.14.2 and 0.1.0 shipped on 3.14.8, so a newer standalone build can change what is bundled; compare with `tools/macho-minos.py` every time; (4) a session restart kills ordinary background processes: run long steps detached (`subprocess.Popen(start_new_session=True)`; macOS has no `setsid`) and log to a file.

## Not in 0.1.2

Intel and Linux packaging, a `shotfleet update` command, a signed update manifest, bit-for-bit reproducible builds (`research/limits-release-engineering-2026-10-05.md` explains why each waits), and anything that needs hardware that does not exist here.
