# Releasing shotfleet: build, test, gate, publish, verify, roll back

The rule: **publish the bytes you tested, never a rebuild.** `packaging/release.sh` (build and deploy in one run, used once by `go-live.sh`) ships different bytes than it tested; use the steps below instead.

1. **Preflight** (read-only, about a minute): `packaging/preflight.sh`. Signing certificates present and not close to expiry, `notarytool history` with the keychain profile, `wrangler whoami`, clean git tree, free disk, the uv standalone Python 3.14 at macOS 11.0. Fix every FAIL first.
2. **Build** from a clean worktree of the commit to release. The build uses pinned inputs and needs no wrapper: it makes a fresh venv from the recorded standalone Python (`uv python install 3.14.2`, found with `uv python find 3.14.2 --managed-python`; any other version or a Homebrew Python is refused before anything is built) and installs ONLY `packaging/requirements-build.txt` with `pip install --require-hashes` (PyInstaller 6.22.3, pyinstaller-hooks-contrib 2026.8, certifi 2026.6.17 and their dependencies, exact versions and sha256 of the wheels). A hash mismatch stops the build with pip's message; do not build until you know why.
   `DEVELOPER_ID=... INSTALLER_ID=... NOTARY_PROFILE=ShotfleetNotary packaging/build.sh`
   (defaults in `packaging/release.sh`). With `NOTARY_PROFILE` set it first runs `packaging/notary-check.sh` (read-only `notarytool history`), which stops before building, and runs it again right before each upload to Apple (in `build.sh` and `pkg.sh`). "No Keychain password item found" usually means the screen locked: macOS locks this keychain about 5 minutes after the screen locks. Unlock the Mac and run again; only if it still fails, store the profile again (the check prints the command). `release.sh` runs the build under `caffeinate -di` so the Mac stays awake. Without `NOTARY_PROFILE`, `build.sh` and `pkg.sh` only sign (on purpose: `tools/release-candidate.sh` relies on that). It signs, notarizes, writes `dist/shotfleet-<version>-macos-arm64.tar.gz` and `.pkg`. Copy both out of `dist/` to a durable folder: the next build deletes `dist/`. Offline: `PIP_NO_INDEX=1 PIP_FIND_LINKS=<folder with those wheels>` (the hashes are still checked). To change a pin, follow the comment at the top of `requirements-build.txt` and record the new versions in the release record. `PINNED_PYTHON` changes the recorded Python on purpose; the pins were taken for 3.14. `tests/test_pinned_build_inputs.py` keeps the file and the script honest. Not covered: PyInstaller's own build-to-build differences (see `research/limits-release-engineering-2026-10-05.md`), `pip` inside the venv (the one that ships with Python 3.14.2) and the Python inside the Linux image (the Dockerfile pins `python:3.14.2-slim-trixie` by digest; `requirements-build.txt` also holds PyInstaller's Linux wheel hashes, so `build-linux.sh` and the image check hashes too).
3. **Verify the build** (read-only): `tools/verify-release.sh <tarball> <pkg>`. Every Mach-O file verifies, team id 2357A78TMR, hardened runtime, a quarantined `--version` run, `tools/macho-minos.py` at or below 13, and for the pkg `spctl` and `stapler`. Ends with PASS or FAIL.
4. **Test and gate those exact files:** `tools/check-claims.sh` (exit 0), then the device gate in `docs/device-queue.md` order (`tools/fixture-e2e.sh --android --keep` with `SHOTFLEET_BIN` on the unpacked build). A rebuild after this point voids the gate.
5. **Record what was tested:** `packaging/publish.sh --make-manifest <version> <tarball> <pkg> > manifest.txt` (version, size, sha256). Keep the manifest with the files.
6. **Publish** from a fresh worktree of `origin/main` (the release merged, `shotfleet.py`, the top `CHANGELOG.md` heading and the docs "Last checked against version" line all say the version):
   `SHOTFLEET_RELEASE_DIR=<durable folder, not /tmp> packaging/publish.sh --dry-run --manifest manifest.txt --artifacts <folder> --checkout <Gumroad URL>` first; it checks everything and prints the plan.
   The real run is the same command without `--dry-run`, and needs the owner's go-ahead. It refuses a file that differs from the manifest, a version that disagrees, a dirty tree, HEAD not `origin/main`, or an unreadable live version id; stages the files in `site/public/download`; archives the shipped bytes and what was live before in `$SHOTFLEET_RELEASE_DIR/archive/`; writes the current Cloudflare version id to `$SHOTFLEET_RELEASE_DIR/state/rollback-<version>-<time>.txt`; stages `site/public/download/<version>/` for this release and for every earlier version kept in `$SHOTFLEET_RELEASE_DIR/archive/<X.Y.Z>/` (see below); runs `wrangler deploy`; checks the served files' hashes, every versioned file, `VERSION`, `install.sh`, `tools/golive/smoke.sh` and a live install into a temp HOME; **rolls back by itself on any failure** (also if the script is stopped).
   **Versioned URLs.** `/download/<file>` and `/download/VERSION` are the latest (`Cache-Control: no-cache`); `/download/<version>/shotfleet-macos-arm64.tar.gz`, its `.sha256` and `.pkg` are permanent and never change (`public, max-age=31536000, immutable`, `site/public/_headers`). A Cloudflare deploy replaces every static asset, so a version survives only if `publish.sh` stages it again: it re-stages each `archive/<X.Y.Z>/` on every run, and first checks every file there against the folder's `SHA256SUMS` and, when kept, its `manifest.txt`; one mismatch refuses the whole publish. `live-before-*` folders are records and are never staged. To add an older release by hand (once): make `archive/<X.Y.Z>/` with `shotfleet-macos-arm64.tar.gz` (and `.pkg` if its hash is recorded) and a `SHA256SUMS` written from the RECORDED hashes (release evidence or manifest), never from the files themselves. Limits: Workers static assets allow 25 MiB per file and 20,000 files per version on the free plan (100,000 paid), no total size cap ([Cloudflare Workers limits](https://developers.cloudflare.com/workers/platform/limits/)); a release is 4 files of about 10 MB. A rollback to a deployment made before a version was staged removes that version's folder until the next publish.
7. **Verify live** (already done by step 6; repeat by hand any time): `env -i sh tools/golive/smoke.sh https://shotfleet.com <Gumroad URL>`.
   **Then bump Homebrew:** `sh tools/bump-homebrew.sh <version> <checkout of noloman/homebrew-tap>` (reads the published `/download/<version>/` `.sha256`, checks it against the tarball, rewrites `Casks/shotfleet.rb`, prints the diff, never pushes); run `brew audit --new --strict --cask noloman/tap/shotfleet` on it, then commit and push the tap yourself.
8. **Roll back by hand** if something turns up later: `cd site && npx wrangler@latest rollback <id from state/rollback-*.txt> -y`, then check `curl https://shotfleet.com/download/VERSION`. A site deploy from a tree without `site/public/download` can delete the downloads: only ever deploy through `publish.sh`.
9. **Linux `check` image** (by hand, after step 6, from the same clean `origin/main` worktree): `gh auth token | docker login ghcr.io -u noloman --password-stdin`, then `packaging/docker-check.sh`. It builds the `Dockerfile` for amd64 and arm64 (the compiled program, Tesseract, aapt2; no `shotfleet.py` inside) and pushes `ghcr.io/noloman/shotfleet-check:<version>` and `:latest`, then runs `--version` from the registry on both CPUs. The token needs the `write:packages` scope (`gh auth refresh -h github.com -s write:packages`). `PUSH=0` builds into the local Docker only. The Action `noloman/shotfleet-check-action` pins the image by version: bump its `Dockerfile` and tag after this step.

`publish.sh` is rehearsed with fakes in `tests/test_release_scripts.py` (a fake wrangler and a local web server) and, since 2026-10-05, once against the real Cloudflare on the throwaway worker `shotfleet-staging`.

**Rehearse on staging** (before changing `publish.sh`, or to practise): `site/wrangler.staging.toml` is the worker `shotfleet-staging`: no routes, no custom domains, no bindings (no KV, rate limiter or email), only its own address `https://shotfleet-staging.manulorenzop.workers.dev`. Run the same command as step 6 with `--staging` and `PUBLISH_BASE=https://shotfleet-staging.manulorenzop.workers.dev` (there is no default base in staging mode). `--staging` passes `--config wrangler.staging.toml --name shotfleet-staging` to every wrangler call, prints the target before each write, keeps its state in `$SHOTFLEET_RELEASE_DIR/staging`, skips only the http-to-https smoke check (workers.dev does not redirect), and refuses when the staging config names the production worker or has a route, a custom domain, a binding, `[env.*]` or any table but `[assets]`, or when the base URL is not the staging address. Roll back by hand with `npx wrangler@latest rollback <id> --config wrangler.staging.toml --name shotfleet-staging -y`. A first run on a brand new staging worker needs one previous version to roll back to: deploy any earlier build once with `npx wrangler@latest deploy --config wrangler.staging.toml --name shotfleet-staging`.
