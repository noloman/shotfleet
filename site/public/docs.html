shotfleet documentation

This page covers how to install shotfleet, take your screenshots, check them and hand them to fastlane. If something here is wrong or unclear, email me at hello@shotfleet.com.

Requirements

  • Built for macOS 13 or later on Apple silicon. My full runs, with simulators and emulators, were all on macOS 27. On macOS 14 and 15 I ran the installer, doctor and check for version 0.1.1, and on macOS 26.2 in a virtual machine for 0.1.2. Other macOS versions are not tested yet.
  • Tested with Xcode 27.0. The default simulator is the iPhone 17 Pro Max, which needs Xcode 26 or newer; with an older Xcode set device_type in the config. Xcode 26.x has not been run.
  • macOS on Apple silicon only. The installer refuses Intel Macs.
  • Maestro 2.x (tested with 2.0.10 and 2.11.0) and Java 17+ (Maestro needs it).
  • Xcode for iOS, the Android SDK for Android.
  • shotfleet doctor --fix downloads what doctor found missing (Maestro 2.11.0, a Java 21 runtime, the Android command-line tools) after showing the plan and asking once; it never uses sudo and does not touch Xcode.
  • Android needs API 33+ emulators for per-app languages. shotfleet finds the SDK in ANDROID_HOME, ANDROID_SDK_ROOT, ~/Library/Android/sdk, Homebrew's android-commandlinetools, or next to an adb on your PATH, and uses any installed arm64 google_apis or google_apis_playstore image of API 33 or newer (or the system_image from the config). shotfleet doctor prints the sdkmanager commands for whatever is missing. The first Android run creates its own emulator, shotfleet_android, from that image; your other emulators are not touched.
  • The installed program brings its own Python. Running from source needs Python 3.11+.

Install

curl -fsSL https://shotfleet.com/install.sh | sh   # then open a new Terminal window
shotfleet doctor --fix           # checks Maestro, Java, Xcode, Android SDK; shows what is missing, asks once, then fetches Maestro and Java

Make sure the right Xcode is selected (xcode-select -p shows which one). If your app is iOS only, you can ignore the Android part of doctor. The first doctor can take a minute while macOS gets its text recognition ready. You only need shotfleet activate <your key> (the key is in your Gumroad receipt email) after your first run, when you want every language. check works without a licence.

The installer downloads the Apple silicon archive, compares it with its published SHA-256 checksum, and puts a link to shotfleet on your PATH. shotfleet check is free for everyone, and run is free for up to 2 languages. A licence unlocks every language and export; see licence and refunds. Without a valid licence, run captures only 2 languages (the first two of your app's languages unless you pick them with --locales de,ja) and says so on a line that starts with "free tier:"; the exit code is 0 if those two pass. If SHOTFLEET_KEY is set but refused, that line says why. check, doctor and init are always free.

To update, run the install line again. It replaces the program and keeps your licence (the key is stored outside the program folder). shotfleet doctor tells you when a newer version is out. A year of updates is included.

There is also an installer you can double-click. Each release is published as a signed, notarized package, https://shotfleet.com/download/shotfleet-macos-arm64.pkg. It puts the program in /usr/local/lib/shotfleet and links shotfleet into /usr/local/bin; macOS asks for your password. Use it if you can't use the curl line, or if a browser-downloaded copy shows "Apple could not verify ...".

Quickstart

Build the app once for the simulator in Xcode (Debug) first, then, in your project folder:

shotfleet init
shotfleet init path/to/MyApp.app path/to/app-debug.apk   # or name a simulator build (Debug-iphonesimulator) and/or an APK yourself

shotfleet init without arguments only reads folders, never builds. For iOS it takes the newest Debug-iphonesimulator app in Xcode's default DerivedData folder (~/Library/Developer/Xcode/DerivedData) whose info.plist points at an Xcode project in this folder, up to two folders below it, or above it. For Android it takes the newest debug APK under build/outputs/apk/debug in this folder or up to two folders below it (app/build/outputs/apk/debug, <module>/build/outputs/apk/debug, android/app/build/outputs/apk/debug; a flavour folder such as apk/free/debug counts too). It prints which build it chose and how old it is. If it finds nothing it exits with the exact xcodebuild and ./gradlew assembleDebug commands to run; then run shotfleet init again.

  1. Edit the generated flow.yaml: Maestro steps in English. Navigate by the text users see and add a takeScreenshot: for each store image. No appId is needed: shotfleet uses each build's own id, so one flow serves iOS and Android.
  2. Try one language: shotfleet run --locales en
  3. When you want every language: shotfleet activate <your key> (from your Gumroad receipt email; check and 2 languages in run work without one).
  4. Run them all: shotfleet run (finds ./shotfleet.toml; both platforms if the file has both, --platform ios for one).
  5. Review out/index.html (out-ios/ and out-android/ if the config has both platforms). It is a grid with a row per language and a column per screen, and problems are outlined in red.
  6. Export to fastlane: shotfleet export out --fastlane fastlane/ (out-ios or out-android if the config has both). That writes deliver's screenshots/<locale>/ or supply's metadata/android/<locale>/images/phoneScreenshots/. Languages that failed a check are skipped, so a bad screenshot never reaches a listing.
shotfleet run --locales en
shotfleet run
shotfleet run --platform ios
shotfleet export out --fastlane fastlane/

Uploading

shotfleet stops at fastlane's folders, and fastlane does the upload. These commands upload the screenshots and leave everything else alone:

# App Store: replaces the screenshots of every language folder in fastlane/screenshots
fastlane deliver --skip_binary_upload --skip_metadata --overwrite_screenshots --force

# Google Play: uploads metadata/android/<locale>/images/phoneScreenshots
fastlane supply --skip_upload_apk --skip_upload_aab --skip_upload_metadata --skip_upload_changelogs --skip_upload_images

Run shotfleet check fastlane/ right before uploading: export already skips languages that failed, and the check also catches folders you edited by hand.

How it works

shotfleet reads the translations compiled into your app and rewrites every selector in the flow to match any translation of that English label. If "Next" has two keys, German matches (Nächste|Weiter). Selectors that use id: pass through untouched.

  • iOS: strings come from *.lproj/*.strings inside the .app; the language is set with launch arguments -AppleLanguages (de); N simulators, iPhone 17 Pro Max (1320x2868, App Store 6.9"); the status bar is overridden with simctl status_bar (9:41, full battery); one sharded Maestro run.
  • Android: strings come from aapt2 dump resources of the APK, keeping only languages the app itself has; the language is a per-app locale set with cmd locale set-app-locales (Android 13+); N read-only emulators at 1080x1920; SystemUI demo mode (9:41, full battery, no notifications); rounds of one language per emulator.

Fresh state: each language starts from a clean install. On iOS that is clearState; on Android shotfleet clears the app data itself, because clearState would also erase the app language.

Check screenshots you already have

If you already have screenshots, from fastlane snapshot, screengrab or by hand, you can check them without capturing anything:

shotfleet check fastlane/ --app path/to/MyApp.app          # deliver: screenshots/<locale>/
shotfleet check fastlane/ --app path/to/app-release.apk    # supply: metadata/android/<locale>/images/phoneScreenshots/

Store codes are mapped back to your app's languages (de-DE to de, no to nb, zh-CN to zh-Hans). The report (check.json and index.html) goes to ./shotfleet-check (change it with --report), and your fastlane folders are never touched. After capture or on an existing folder, every screenshot's text is compared against your app's own strings. On iOS, shotfleet reads the text straight from the app while each screenshot is on screen; otherwise, and for screenshots made by other tools, it uses macOS's built-in text recognition. It reports:

  • Wrong language: the German folder actually shows English or Japanese strings.
  • Copies: the same image in two languages.
  • Blank: a screenshot with nothing drawn but the status bar: an app that paints its first frame after the flow's wait passed (Flutter debug builds and Compose do). run captures that language again once, then reports it; wait for text on the screen before takeScreenshot.
  • Missing: a language that did not produce every screenshot.
  • Translation collisions, before anything runs: for example tr: 'Next' -> 'İleri' also means 'Advanced'. A tap could hit the wrong button there, so you anchor that step with below: or use an override.
  • Store rules: sizes each store accepts (every App Store display class, Play's 320 to 3840 px), at most 10 (App Store) or 8 (Play) per listing, no transparency, a 6.9" or 6.5" iPhone set, a 13" iPad set when the app runs on iPad. Screenshots made in other tools work too: Apple Watch, Mac, Apple TV and Vision Pro sizes are known (3840x2160 is both Apple TV and Vision Pro), and one Watch size is required in every language.
  • Languages your app does not have: a store listing (say Traditional Chinese) whose screenshots cannot be in that language because the app is not translated into it.

check without --app relies on language detection, which cannot judge short screens; pass --app for the full check.

export also takes a plain <locale>/*.png folder of such a set (Apple Watch, Mac, Apple TV, Vision Pro) once shotfleet check <folder> --report <folder> has written its check.json there; it copies the set into screenshots/<locale>/ next to your iPhone and iPad sets. Size and count rules only: shotfleet captures iPhone, iPad and Android screens, not these.

Config

The whole config can be this (shotfleet init writes it):

[ios]
app = "path/to/MyApp.app"

[android]                 # optional: the same file and flow serve both platforms
apk = "path/to/app-debug.apk"

Everything else is read from the build or has a default; set it only to change it. A typo or a wrong type is refused with a one-line message before anything runs.

Flutter, React Native, .NET MAUI, Unity and translation-platform exports

These frameworks do not keep their translations in a form shotfleet can read inside the built app, so point it at the source files instead. Add strings to either section (globs, relative to the config):

strings = "lib/l10n/*.arb"                      # Flutter
strings = "src/locales/*/translation.json"      # React Native / Expo with i18next
strings = ["Resources/Strings/*.resx"]          # .NET MAUI

Supported: .arb, i18next and react-intl .json (nested keys, _one and _other plurals), .xcstrings, .strings, .stringsdict, Android and Compose strings.xml, XLIFF (.xlf, .xliff), .resx, gettext .po, .properties, and CSV with one column per language (Unity Localization, spreadsheets). ICU plurals and placeholders (%d, %1$@, {name}, {{name}}) are understood. The language comes from @@locale, the file name (app_de.arb, Resources.de.resx) or the folder (locales/de/, values-de/). check takes the same files:

shotfleet check fastlane/ --strings 'lib/l10n/*.arb'

Hooks

Nothing here is on by default: a config without these tables behaves exactly as above. Hooks run your own commands (/bin/sh, in the config's folder, output on stderr) around a run and an export:

[hooks]
before_run   = "make build-sim"                 # a string, or a list of commands run in order
after_run    = 'curl -sS -X POST -H "Content-type: application/json" "$SLACK_WEBHOOK_URL" --data "{\"text\":\"shotfleet $SHOTFLEET_PLATFORM: $SHOTFLEET_PROBLEMS problem(s)\"}"'
before_export = "git diff --quiet"              # a non-zero exit stops the export
after_export  = 'fastlane deliver --skip_binary_upload --skip_metadata --overwrite_screenshots --screenshots_path "$SHOTFLEET_FASTLANE/screenshots"'
# hook_timeout_s = 1800                         # default 600 per command

A failing before_* hook stops the command (exit 2); a failing after_* hook makes the exit code 1, so CI notices. Variables on every event: SHOTFLEET_EVENT, _VERSION, _CONFIG, _PLATFORM, _OUT; before_run and after_run also get _BUNDLE_ID and _LOCALES (empty unless restricted); after_run gets _EXIT, _PROBLEMS, _REPORT (<out>/check.json); the export hooks get _FASTLANE, _REPORT (and _EXIT after the export). --no-hooks skips them for a dry run.

Overrides

Overrides replace what shotfleet would tap for one language. They are the fix for a collision warning ('Next' -> 'İleri' also means 'Advanced') and for labels that are not in your app's strings:

[overrides.tr]                         # the language as shotfleet names it: tr, pt-BR, zh-Hans...
"Next" = "İleri"                       # literal text
"Advanced" = "re:Gelişmiş.*"           # "re:" = a regular expression
"Search" = "Ara"

Inputs

Inputs set the text a flow types, per language. Write inputText: ${name} in the flow and give the values in the config:

[inputs]                               # typed in every language that has no value of its own
name = "Alex"
[inputs.ja]                            # the language as shotfleet names it; pt covers pt-BR too
name = "田中"

The value goes into that language's flow as a Maestro env: entry. This works on iOS. Maestro hands any flow to any emulator, so on Android a name that has a per-language value is read from a small script (shotfleet_vars.js) that picks the emulator's row by MAESTRO_DEVICE_UDID. Maestro 2.11.0 sets that variable to the emulator's serial: German and Japanese values showed up as typed in screenshots (device run 2026-10-04, one emulator, one language after the other; two emulators at once and Arabic not run). Maestro 2.0.10 does not define it, so on 2.0.10 Android runs type the [inputs] defaults only. Check the first screenshots in a script like Japanese or Arabic. Text you type is not translated by itself: it stays the same in every language unless you set [inputs] (iOS; on Android it needs a Maestro that sets MAESTRO_DEVICE_UDID, which 2.11.0 does and 2.0.10 does not).

Device setup

Device setup runs your own commands once per simulator or emulator, right after it boots (iOS: after the status bar is set), so an app with a screenshot switch, dark mode, a location or a granted permission looks the way you want:

[ios]
simctl = ["ui $UDID appearance dark", "location $UDID set 52.3676,4.9041"]   # xcrun simctl <args>; $UDID is the simulator's id
[android]
shell = ["setprop debug.myapp.demo 1", "settings put system font_scale 1.0"]  # adb -s <serial> shell <command>

A command that fails stops the run before anything is captured (exit 2) and prints the command. iOS commands apply to every language: one Maestro process serves all simulators, so a different command per language is not possible. The Android commands are unit-tested as command lines; whether a given setprop or settings command takes effect on your emulator image has not been tried on a real one.

Expected content

Expected content checks that what you seeded is really on screen, per language. Name the screenshot as in the flow (takeScreenshot: 01_home):

[expect.01_home]
any = ["Senior iOS Engineer"]          # at least one of these is on screen
[expect.01_home.de]                    # only for the German screenshot (pt covers pt-BR)
all = ["Steinmännchen"]                # every one of these is on screen
[expect.03_log]
not = ["No workouts yet", "Keine Workouts"]   # the empty state must not show

run checks these automatically; for screenshots you already have, use shotfleet check out/ --content shotfleet.toml (free, no licence). A missing or forbidden text is a problem line, and a table for a screenshot that does not exist is reported too. Case, accents and spacing are ignored. On iOS the text is the app's own, so a match is exact in any script. On Android it is read from the picture: a text in a script macOS cannot read (Greek, Hebrew, most Indic) is reported as a note, could not verify, never as a pass. This proves the strings you list are present, not that the data looks right.

Plugins and the rest

shotfleet foo runs shotfleet-foo from your PATH (like git and gh), when foo is not a built-in command. run, check and export take --json and use stable exit codes, so they script like any other tool; SHOTFLEET_OCR or --ocr-command swaps the text reader; strings = "glob" swaps the translation source.

Licence

shotfleet activate <key> stores your key on this Mac. The key from your Gumroad receipt has 3 activations. Activating again on a Mac that still has the key saved counts nothing; after shotfleet deactivate, a new macOS install or a new user account, the same Mac counts again. shotfleet deactivate removes it from this Mac but does not give the activation back; if you run out, email hello@shotfleet.com and I'll reset the count. The licence is checked online when you activate and about once a week after; if the server cannot be reached, the Mac keeps working for up to 30 days after the last good check. A refunded or disabled key is refused at its next check; check and the 2 free languages keep working and nothing you made is deleted. In CI, set SHOTFLEET_KEY (no activation is used): that check fails open, so with the licence server unreachable the run counts as licensed and a CI key has no offline limit (see In CI).

The messages you may see are "that key didn't activate: <reason>", "the key was disabled, as Gumroad does after a full refund" and "this licence is no longer valid". Terms and refunds are on the licence and refunds page.

In CI

run, check and export take --json: the result goes to stdout as JSON (exit, screenshots, problems and notes for run and check, merged over every device or platform checked, plus reports (one {report, problems} each) when there are several; exit, exported, skipped for export) and progress goes to stderr. Exit codes: 0 all good, 1 problems found, 2 setup error (the message says what to fix), 130 interrupted.

Checking needs only a Mac (it uses macOS text recognition), with no simulators, so it fits a pull-request job on GitHub's macOS runners. check is free and needs no licence. The recipe as written (the build step, then check with --app) has not been run on GitHub yet. The installer, shotfleet --version, doctor and check on sample screenshots did run on GitHub's macos-14 and macos-15 runners (2026-10-05).

# .github/workflows/screenshots.yml
on: pull_request
jobs:
  check-screenshots:
    runs-on: macos-15
    steps:
      - uses: actions/checkout@v4
      - run: xcodebuild -scheme MyApp -sdk iphonesimulator -configuration Debug -derivedDataPath build build
      - run: curl -fsSL https://shotfleet.com/install.sh | sh   # Apple silicon runner
      - run: shotfleet check fastlane/ --app build/Build/Products/Debug-iphonesimulator/MyApp.app --json > check.json
      - uses: actions/upload-artifact@v4
        if: always()
        with:
          name: screenshot-check
          path: |
            check.json
            shotfleet-check/

To use run or export in CI, set SHOTFLEET_KEY to your licence key (keep it in a secret). It is checked online on each run and uses none of your 3 activations. This check fails open on purpose: if the licence server cannot be reached, the run counts as licensed, so a CI job never fails because Gumroad is down. A CI key has no offline time limit and nothing is stored for it, so while Gumroad is unreachable it is not re-checked: a refunded or disabled key keeps working until a run reaches Gumroad, and an outage looks the same as a good key. A Mac where you ran shotfleet activate is different: it re-checks about weekly and stops after 30 days offline. With an invalid key, export refuses and run captures only 2 languages. Which two: the first two of your app's languages, unless you pick them with --locales de,ja; run says so on a line that starts with "free tier:", and if the key is refused that line says why.

With --json, progress goes to stderr, including the "free tier:" line, so a CI job that must capture every language should fail when that line appears, or compare the language count in run.json.

With AI agents

shotfleet mcp is an MCP server with check, run and doctor tools. Add it to Claude Code with claude mcp add shotfleet -- shotfleet mcp, or to any MCP client as the command shotfleet mcp.

There are also three agent skills that ship with the program: shotfleet (install, set up, run, check and troubleshoot), shotfleet-ci (add shotfleet check to CI) and shotfleet-review (turn a check report into a fix list). Claude Code, Cursor, Codex, Gemini CLI and GitHub Copilot all load skills from a folder. One command puts them in the right folders:

shotfleet skill install
shotfleet skill install --project
shotfleet skill install --dir <folder>

shotfleet skill install copies them into ~/.claude/skills (Claude Code and Cursor read it) and ~/.agents/skills (Codex, Gemini CLI, GitHub Copilot and Cursor read it). With --project they go into ./.claude/skills and ./.agents/skills in your project, so you can commit them for your team. --dir <folder> copies them into one folder you choose. Skills that are already there are kept unless you pass --force. Start a new agent session after you install them.

The skills are also in a public repo, so you can install them without shotfleet first. In Claude Code: /plugin marketplace add noloman/shotfleet-skills, then /plugin install shotfleet@shotfleet (the skills plus the MCP server). For other agents: gh skill install noloman/shotfleet-skills --all --scope user. More in the repo's README.

Your licence key: on your Mac, run shotfleet activate once yourself. After that your agent uses the CLI and never sees the key. In CI, use the SHOTFLEET_KEY secret. Don't pass the key with claude mcp add --env: it ends up in plain text in ~/.claude.json.

Limits

  • Where strings come from: .strings, .stringsdict and String Catalogs on iOS (including those in frameworks, Swift packages and a Watch app), strings.xml and <plurals> on Android, and Compose Multiplatform resources on both. Other frameworks read source files (see above). Labels with numbers ("Round 2 of 12") are matched and translated with the same numbers, in every plural form.
  • Flutter and React Native work from your translation files (run end to end on a real Flutter app, wger, and a real Expo app, the obytes template, on iOS and Android, 2026-10-03; other apps and bare React Native not yet run).
  • If you pass init, run or check a Flutter, React Native, .NET MAUI or Unity build, shotfleet tells you what to add: a hint: on stderr with the strings = line for your translation files, and a warning for a Flutter debug build (DEBUG banner) or a React Native Debug build (Metro dev server). It detects these builds from file names in the bundle, so it may miss some versions, and it never stops a run.
  • Text recognition is macOS's. It reads 33 languages (the macOS 27 number; older macOS versions read fewer), including Latin, Cyrillic, Arabic, Thai, Devanagari, Chinese, Japanese and Korean scripts. A language outside that list but written in Latin script (Catalan, Croatian, Hungarian, Slovak, Slovenian) is judged by language detection on every macOS, like a listed one; macOS reads it with its Latin model, and accents can be lost (Hungarian). Older macOS versions list fewer languages, so on those more of your languages fall under this rule (not tested on macOS 13). For scripts it cannot read (Greek, Hebrew, Armenian, Georgian, most Indic and Southeast Asian scripts), check still catches screens in another language, copies and missing screens, and says which screens it could not read.
  • If macOS text recognition stops answering (the first time, macOS compiles its text model in ANECompilerService, which can take minutes on a loaded Mac), check waits while that compile is working, up to 6 minutes. If it still gets no answer it says what happened and switches to Tesseract when it is installed (brew install tesseract tesseract-lang), saying so in its output; otherwise it tells you to wait for the first compile and re-run, close heavy apps, or install Tesseract. A restart is a last resort. iOS runs mostly aren't affected: they read the app's own text, and only screens where that text proves little go to OCR.
  • For full verification of those scripts, give check an OCR that reads them, for example Tesseract (about 700 MB): --ocr-command "tesseract {image} stdout -l {tesseract}" (or set SHOTFLEET_OCR). It is used only for languages macOS cannot read; {lang} is the language code if your tool wants that instead.
  • Free memory before a run: idle Gradle daemons can hold gigabytes. Run ./gradlew --stop (once per Gradle version you use) before shotfleet run, and close apps you do not need. Four simulators on a loaded Mac can take many times longer.
  • Permission prompts ("Allow While Using App", "Don't Allow") are drawn by iOS and Android in the device language, which stays English even while your app runs in German. Write those taps in English; shotfleet keeps the English text matchable. Better still, skip the prompts: on iOS start the flow with a launchApp block that has permissions: all: allow (shotfleet adds its language arguments to your options). On Android shotfleet installs with every permission granted.
  • Dialogs that appear late (disclaimers, consent screens): dismiss them in a loop until your first real screen is visible, not with a fixed wait. Longer languages push buttons off-screen: add scrollUntilVisible before tapping them.
  • Flutter rows and cards are one label: Flutter joins a row's title and detail line into one label with a newline (Self-hosted\nConnect to your own instance), so tap it as "Self-hosted.*"; shotfleet translates the part before the .* (.*Register works too). A line like New to wger? Register is one label as well.
  • A language the app only half translates (wger's Japanese is 30%): the app shows its base language for every missing string. run warns when you ask for such a language by name, and check reports the screenshots that came out in the base language.
  • Building the app on Xcode 27 (found on wger, the obytes template and kotlinconf-app, 2026-10-03; not shotfleet's doing, but it stops you before the first screenshot): npx expo run:ios ends with "Can't determine id of Simulator app" because Xcode 27 has no Simulator.app, so build the generated project yourself, xcodebuild -workspace ios/.xcworkspace -scheme -configuration Release -sdk iphonesimulator -derivedDataPath ios/build build IPHONEOS_DEPLOYMENT_TARGET=15.1 (Xcode 27 refuses the old deployment targets of some pods), and init finds it in ios/build. A Kotlin Multiplatform app needs ARCHS=arm64 on its xcodebuild ("Architecture Not Configured in Gradle: ios_x64"; init prints it).
  • Typing a password on iOS in Arabic: inputText into a secure (password) field drops Latin letters when the app runs in Arabic (seen on the Expo app, iOS 26.4: abcdef typed nothing, abc123 typed only 123, 123456 typed all six); name and e-mail fields are fine. Use digits for a demo password.
  • Linux: check and the Android readers run from source on Linux: they need Tesseract, there is no Linux installer yet, and run on a Linux emulator has not been tried. iOS needs a Mac.
  • iOS 27: one simulator and one language ran with 0 problems (2026-10-05). A run on four simulators at once has not been tried on iOS 27; pin an older runtime if you need a tested setup.
  • Run times depend on the Mac and on Maestro: in one run of my app on my M1 Pro with 4 simulators and Maestro 2.0.10, 18 languages took 9 minutes on iOS and 15 on Android; on Maestro 2.11.0 shotfleet retried some iOS languages because a simulator's driver started slowly.
  • shotfleet uploads nothing to a store: fastlane does that (see Uploading above).
